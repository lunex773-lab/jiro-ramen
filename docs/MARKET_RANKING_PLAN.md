# 共通市場・企業間ランキング 実装計画（仕様書 11 章・Phase 1 の提出物）

作成日: 2026-11-04。前提の監査は `MARKET_RANKING_AUDIT.md`（矛盾 C1〜C11）。
**この計画のうち「論点」と書いたものはオーナーの判断待ち。判断が出るまで新しい市場の実装は始めない**（仕様書 10 章「独断で既存機能を削除・変更しない」）。

## 1. 全体の形（既定案）

```
            ┌───────────── D1（台帳・集計） ─────────────┐
            │ communities / community_members             │
            │ companies（企業の登録。どのコミュニティか）  │
            │ company_days（企業×ゲーム内日付の確定値）    │
            │ rank_agg（企業×期間×種別の集計。upsert）     │
            │ rewards（一意キーで二重受領を防ぐ）          │
            │ sync_runs（JST 期間ごとの同期の記録）        │
            │ audit_log（既存。不正の疑いもここへ）        │
            └───────────────▲──────────────▲──────────────┘
                            │              │
  JST 0:00 のアラーム ─▶ CommunityDO（今の MarketRoom を作り替える。コミュニティ1つ = 1つ）
                         ・期間の確定、同期目標（最大の日付）の決定、各社の同期の状態機械
                         ・日付ごとの「店の見込み」の記録（客の取り合いを同じ日付の相手と計算する）
                            │ 自動営業の依頼（期間ID・目標日付つき＝冪等）
                            ▼
                         CompanyDO（企業1つ = 1つ。コミュニティより長く残る）
                         ・企業の GameState（今の会社の層そのまま）と自動経営方針
                         ・自動営業を分割して実行（アラームで続きから）
                         ・手動プレイの日の確定（論点 1 で方式が決まる）
```

- **企業は CompanyDO に出す**（C3）。コミュニティが終わっても企業・資産・従業員・店舗・在庫・評価・履歴はそのまま残る（仕様書 6.2）。
  コミュニティは「どの企業がどの期間に競ったか」の記録と、客の取り合いの相手を決めるだけにする
- **時計は JST の日付だけ**（C1）。今の「600秒ごとに1日」の時計は使わない。
  期間ID は `YYYY-MM-DD`（JST）。期間の境界は `Asia/Tokyo` で計算し（日本は夏時間がないので UTC+9 固定で計算できるが、関数は1か所にまとめてテストする）、端末の時刻は使わない
- **進行の上限は付けない**。1回の要求で計算する量の上限（分割）はあるが、残りはアラームで続ける。これは上限ではなく分割（仕様書 3.2）

## 2. 0時の同期（仕様書 3.4・3.5 の状態機械）

コミュニティごとに `sync_runs` の1行（期間ID × コミュニティ、一意）と、企業ごとの状態を持つ。

| 段階 | 内容 | 失敗したとき |
| --- | --- | --- |
| `closing` | 0:00 を過ぎたら期間を締める。各社の「その期間に確定した手動の日」を確定（以後に確定した日は次の期間に数える） | 何度やっても同じ結果（締めた時刻ではなく期間IDで決める） |
| `target` | 同期目標 = 最も進んだ企業のゲーム内日付。`targetDate` を記録 | 記録済みなら読み直すだけ |
| `syncing` | 不足する企業ごとに CompanyDO へ「期間ID・目標日付まで自動営業」を依頼。各社は済んだ日ごとに `lastProcessedGameDate` を進めて保存 | 済んだ日はやり直さない（日付と期間IDで冪等）。途中で止まってもアラームで続きから |
| `ranking` | 全社が目標に着いたら、その期間に確定した日の集計を `rank_agg` に upsert | 集計は `company_days` から作り直せる（再実行できる） |
| `done` | 新しい期間を開始 | — |

- **同期中の操作**（3.5）: 同期中の企業は閲覧だけ。経済を変える操作は「同期が済むまでお待ちください」で断る（手動プレイの開始も同じ）
- **0時に手動プレイの途中の企業**（C9）: 0:00 の時点で締め、その企業の同期は今の営業日が終わってから行う。
  0:00 以降に終わった日は次の期間に数える（目標は 0:00 の時点の値で固定）
- **全社が目標に着く前に、その期間のランキングを確定しない**（3.5）
- **用語**: `commonMarketDate` = コミュニティの同期済みの日付、`manualProgressDays` = その期間に手動で確定した日数、`autoSimulationDays` = 自動営業で補った日数、
  `synchronizationStatus` / `lastProcessedPeriod` / `lastProcessedGameDate` / `processingVersion`（自動営業の計算式の版。式を変えたら記録に残す）は仕様書 3.3 の名前をそのまま使う

## 3. 客の取り合い（C4）

期間の途中は企業ごとにゲーム内日付が違う。そこで:

- 各社が日を確定するとき、その日の店ごとの「見込み」（今の市場の `competitionFactors` に使う値）を `company_days` に書く
- ある企業の日付 d の客の取り合いは、**ほかの企業の日付 d の見込み**で計算する。相手がまだ日付 d に着いていないときは、相手の最新の見込みを使う（先に進んだ企業が不利にも有利にもなりにくい）
- 同期で後から日付 d を自動営業した企業の見込みも記録されるので、次の期間からは同じ日付の相手と比べられる

**欠点**: 先に進んだ企業は、相手が後で実際に何をしたかを知らずに計算される（非同期の競争なので避けられない）。市場シェアは確定した日の売上から計算するので、最終的な順位はずれない。

## 4. 論点（オーナーの判断が必要）

### 論点 1: 手動プレイの日を、サーバーがどう確定するか（C2）

仕様書は「クライアントの申告を信用しない」「進行日数の改ざんを防ぐ」。今のひとりプレイは端末で実時間に合わせて動くので、端末の結果はサーバーで確かめられない。

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| **A（推奨）** | 市場の企業の手動プレイは**サーバーのルームで遊ぶ**（今の共同経営と同じ仕組み。1人でも部屋を開く）。日の確定はサーバーがする | 今ある仕組みを使える（共同経営で動いている）。改ざんできない。最大4人の共同経営とそのままつながる | 通信が必要（オフライン不可）。サーバーの費用（1日あたり実時間約10分の稼働＝約75 GB-s/人・日。Free の上限で全体で約170人・日/日）。通信の遅れの分、操作の手応えが少し落ちる |
| B | 端末で遊び、**操作の記録をサーバーで再計算**して確かめる | 端末で遊べる（反応が速い）。サーバーは再計算のときだけ | 端末の計算を「固定刻み」に作り替える大きな改修（今は実時間の刻み）。1日の再計算に CPU 約0.5〜0.8秒。記録の形式・検証の仕組みを新しく作る。作り替えの間、ひとりプレイを壊す危険 |
| C | 端末の結果をそのまま受け取り、あり得ない値だけ弾く | いちばん簡単・安い | 仕様書の「申告を信用しない」に反する。ランキングを改ざんできる |

### 論点 2: 自動営業の計算（C5・C6）

仕様書は「同じ経済ルールを可能な限り使う」「単純な加算は禁止」「必ず赤字・極端に劣るのは禁止」。

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | **今の細かいシミュレーションを画面なしで回す**（店主はボットとして働く。能力は手動より低め） | 手動と同じ規則（同じコード）。在庫切れ・従業員不足・故障・イベントも同じように起きる | 重い（約0.5〜0.8秒/店・日）。30日/日のコミュニティ100個で月約5.9億 CPU ミリ秒（Paid で約 $11/月）。Free では約50個まで。長く遅れた企業は追いつくのに時間がかかる（分割して続ける） |
| **B（推奨）** | **今の「店長の営業（1日単位の計算）」を広げる**。同じ需要の式（`arrivalRate` を積分）・同じ容量・同じ価格の反応・在庫・給与・家賃・故障の確率・借入を使い、ランダムイベントと勤怠を足す。細かいシミュレーションとの差をテストで固定する（今は売上 ±1%、営業利益の比 0.87〜1.00） | 約0.03ミリ秒/店・日で、上限なしの進行でも費用がほぼかからない。すでに市場で動いている | 細かい出来事（1人ずつの客・口コミ・常連・調理の失敗）は平均で近似する。「同じコード」ではなく「同じ式」 |
| C | 組み合わせ: ふだんは B、遅れが少ないとき（例: 1社3日以内）だけ A | 近い日は同じコードで計算 | 2つの計算の差が順位に出る（どちらで計算されたかで有利・不利）。仕組みが複雑 |

### 論点 3: コミュニティと企業の関係（C3、仕様書 6.2）

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| **A（推奨）** | 企業は**同時に1つのコミュニティだけ**。終了後も企業は残り、**同じ企業のまま次のコミュニティに参加できる**。参加の時点の状態をランキングの基準にする（成長率・累計はその時点から数える） | 資産が消えない（仕様書どおり）。順位は「参加してからの成長」で比べるので、古い企業が有利になりすぎない | 売上・利益の「額」の順位は大きい企業が有利（成長率のランキングで補う） |
| B | 新しいコミュニティには新しい企業で参加。古い企業は自由に営業を続ける（ランキングなし） | 条件が全員同じで公平 | 企業を育てる意味が薄れる。1人が複数の企業を持つ管理が要る |
| C | コミュニティを作る人が A か B かを決める（「育てた企業で参加」「新規の企業だけ」） | 両方の遊び方ができる | 仕組みと画面が増える。全体ランキングで両方が混ざる |

### 論点 4: 今の「10分ごとに1日」の市場（d4c4228 で公開済み）

| 案 | 内容 |
| --- | --- |
| **A（推奨）** | 新しい仕組みに**置き換える**。今の市場の企業は新しい形（CompanyDO）へ移し、データは消さない。今の市場はまだ公開したばかりで、使っている人はほぼいない見込み |
| B | 「早い市場」という別の遊び方として残す（2つの時計の市場を両方保つ。テスト・画面が倍になる） |

### 2回目に聞く論点（1〜4 が決まってから）

- 全体ランキングの比べ方（C11）: 期間の合計で比べるか、ゲーム内1日あたりで比べるか（コミュニティによって進んだ日数が違う）
- Cloudflare のプラン: Free か Paid か（論点 1・2 の上限が変わる。アカウントの情報はこちらからは見ない）
- 今のゲームにない機能（C8）を足すか: 曜日・季節の需要、疲労、希望シフト、広告予算、短期バイト、営業時間の短縮。
  足すと手動のゲームも変わる（バランスの調整が要る）。足さないものは自動経営の方針から外す
- データのないランキング種別（C7）: 従業員満足度（社員の満足度の平均を新しく作る）・店舗品質（清潔さ・設備の状態・評判から作る）・企業価値成長率（純資産＋事業価値の式を決める）。
  総合評価は、各種別の順位を同じ重みで足す形（根拠のない配点を使わない）を候補として出す
- 株式発行・企業買収（仕様書の方針の一部）: 進化設計書の Phase 5・6 で作るまで、方針の項目は「禁止（固定）」で出す

## 6. 費用の見積もり（論点の案ごと。詳細は監査 6 章）

6社×2店のコミュニティで、1人（最も進んだ企業）だけが1日に30日を手動で進め、ほかの5社を自動営業で追いつかせる場合:

| 組み合わせ | 1コミュニティ・1日 | 100コミュニティ・1か月（Paid の場合） |
| --- | --- | --- |
| 論点1 A ＋ 論点2 B | 手動プレイの部屋 約75 GB-s/日 × 30日 = 約2,250 GB-s、自動営業 約8ミリ秒 | DO の稼働 約675万 GB-s → 込みの40万を超え 約 $80/月 |
| 論点1 A ＋ 論点2 A | 上に加えて自動営業の CPU 約195秒 | 上に加えて CPU 約5.9億ミリ秒 → 約 $11/月 |
| 論点1 B ＋ 論点2 B | 手動の日の再計算 約0.65秒 × 30日 = 約20秒、自動営業 約8ミリ秒 | CPU 約5,900万ミリ秒 → 込みの3,000万を超え 約 $0.6/月（ほかに端末の作り替えの開発） |

Free の場合は1日の上限で止まる（DO の稼働 13,000 GB-s/日 → 論点1 A なら全体で1日約170日分の手動プレイ）。

- 手動プレイをサーバーで動かすと、**いちばん大きい費用は「手動で遊ぶ時間」**（自動営業ではない）。共同経営で遊ぶ人には、今もすでに同じ費用がかかっている
- D1 の書き込み: 企業×日付で1行（`company_days`）。集計は0時の同期で1回だけ upsert する（企業ごとに 4期間×9種別＝36行）。
  6社が30日/日なら 180行＋216行＝約400行/日/コミュニティ（索引の更新も行数に数えられるので実際はその数倍）。Free の10万行/日では数十〜百数十コミュニティまで
- 本番で計測してから上限の警告（費用の監視）を入れる

## 7. 守ること（仕様書 13 章）

- 今のひとりプレイ・共同経営・会社（複数店舗）は消さない・壊さない。今の市場は論点 4 の判断で扱う
- 自動営業は日付を足すだけにしない（論点 2 のどちらでも、需要・在庫・給与・家賃・故障・借入を計算する）
- ランキングはサーバーが確定した日だけで集計する。端末の時計・申告は使わない
- 進行の上限を足さない（分割はする）
- コミュニティの終了で企業・資産を消さない
- 根拠のない倍率・配点を入れない（総合評価は順位の等しい重みを候補にし、オーナーの判断を待つ）
- テストを省いて完了と言わない
