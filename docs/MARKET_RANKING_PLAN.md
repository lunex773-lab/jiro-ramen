# 共通市場・企業間ランキング 実装計画（仕様書 11 章）

作成日: 2026-11-04。前提の監査は `MARKET_RANKING_AUDIT.md`（矛盾 C1〜C11）。
オーナーの判断は 2026-11-04 にすべて出た（3 章）。この計画はその判断に合わせて書き直したもの。

## 1. 全体の形

```
  端末（手動プレイ）                         CommunityDO（今の MarketRoom を作り替える。コミュニティ1つ = 1つ）
  ─────────────────                         ────────────────────────────────────────────
  ① 日の始め  ── day/start ─────────────▶  その日の条件を渡す（ゲーム内日付・曜日・季節・客の取り合いの倍率・状態の版）
                                            0時〜同期が済むまで・同期中・状態が古いときは断る
  ② 1日を端末で営業（通信なしでよい）
  ③ 日の終わり ── day/commit（日報＋終わりの状態）▶ 確かめる（つながり・上限） → 保存・その日を記録
                                            つながらない日は受け取らない（前日に戻す）。上限を超える日は受け取って順位から外す
  ④ 届くまで次の日は始められない

  JST 0:00 のアラーム ─▶ 締め（営業中の日は最大30分待つ） → 同期目標＝最も進んだ企業の日付
                        → 遅れた企業（AI 企業も）を1日単位の自動営業で目標まで（日付ごとに全社そろえて計算）
                        → ランキングの集計を D1 へ → 新しい期間
```

- **企業の置き場所**: 企業は所属するコミュニティの DO の中にある（企業ごとに別の断片で保存）。コミュニティが終わっても消さずに残り、
  手動の営業は続けられる（終了後は0時の自動営業とランキングはない）。「育てた企業で参加」のコミュニティへ移るときは、
  前の DO から書き出して新しい DO に入れ、前の DO には「移った」と残す。どこにいるかは D1 の `market_companies` に記録する
- **時計は JST の日付だけ**。期間ID は `YYYY-MM-DD`（JST）。境界の計算は1つの関数にまとめ（日本に夏時間はないので UTC+9 で計算）、端末の時刻は使わない。
  今の「600秒ごとに1日」の時計はなくす
- **進行の上限は付けない**。1回の要求で計算する日数には上限（分割）があり、残りはアラームで続ける。これは上限ではなく分割（仕様書 3.2）
- 同じ日付の相手と客を取り合う: 各社が日を確定するとき、店ごとの「見込み」（客の取り合いに使う値）を日付ごとに記録する。
  日付 d の倍率は、ほかの企業の日付 d の見込みで計算する（相手がまだ d に着いていなければ、相手の最新の見込み）

## 2. 0時の同期（仕様書 3.4・3.5）

| 段階 | 内容 | 失敗・二重実行のとき |
| --- | --- | --- |
| `closing` | 0:00 になったら期間 P を締める。P のうちに始めた日がまだ営業中なら、届くまで待つ（最大30分。過ぎたらその日は無効で、端末は前日の状態からやり直す）。0:00 から同期が済むまで、新しい日は始められない | 期間ID で決めるので、何度やっても同じ |
| `target` | 同期目標 = 最も進んだ企業の済んだ日付。記録する | 記録済みなら読み直すだけ |
| `syncing` | 目標より遅れた企業を、日付ごとに全社そろえて自動営業する。企業ごとに `lastProcessedGameDate` を進めて保存 | 済んだ日はやり直さない。1回の上限を超えたらアラームで続きから |
| `ranking` | P の日の集計（企業 × 週・月・年・累計）を D1 に upsert | 確定した日の記録から作り直せる |
| `done` | 期間 P+1 を始める | — |

- 同期中は閲覧だけ。経済を変える操作は断る（3.5）。全社が目標に着く前に、その期間のランキングを確定しない
- 仕様書 3.3 の項目: `commonMarketDate`（全社が済んだ日付）・`manualProgressDays`（その期間に手動で確定した日数）・`targetDate`・`autoSimulationDays`（自動営業で補った日数）・
  `synchronizationStatus`・`lastProcessedPeriod`・`lastProcessedGameDate`・`processingVersion`（自動営業の計算式の版）をそのままの名前で持つ

## 4. 端末のデータの確かめ方（判断 1a・1b）

前日の確定した状態 `prev`、届いた状態 `next`、その日の条件 `ticket` から:

- **受け取らない（つながらない）**: 日付が `prev.day + 1` でない、企業・店舗の id が違う、
  `next.money ≠ prev.money + その日の新しい取引の合計`、取引の記録なしに増えた従業員・設備・店舗・融資、
  在庫が「前日＋仕入れ」を超える、従業員の能力が1日で上がれる幅を超える、評判が1日で動ける幅を超える
- **受け取って順位から外す（上限を超える）**: 来客が `ticket` の倍率とその日の状態から出せる見込みの上限を超える、提供が席数と営業時間で出せる上限を超える、
  売上が「提供 × 最も高い客単価」を超える
- 上限の幅は、ボットで多くの日を回した実際の値の最大に余裕を持たせて決め、テストで「ふつうの営業では一度も引っかからない」ことを確かめる

## 7. 守ること（仕様書 13 章）

- 今のひとりプレイ・共同経営・会社（複数店舗）は消さない・壊さない。今の市場は新しい仕組みに置き換え、企業のデータは移す
- 自動営業は日付を足すだけにしない（需要・在庫・給与・家賃・故障・借入・イベントを計算する）
- ランキングはサーバーが受け取った日だけで集計し、上限を超えた日は外す。端末の時計は使わない
- 進行の上限を足さない（分割はする）
- コミュニティの終了で企業・資産を消さない
- 根拠のない倍率・配点を入れない（総合評価は順位の等しい重み）
- テストを省いて完了と言わない

### Phase 5 で決めた細部（判断 15〜18 の範囲内での既定）

- 会社を持っていけるのは、**競争期間が終わった市場**の、営業している（破産・引退していない）自分の会社だけ。持っていく先は「育てた企業も参加できる」市場で、終わる前のものだけ。先にその人の会社があれば入れない
- 持っていく先に空きがなければ、AI 企業のうち市場シェアのいちばん小さい1社が撤退する（新しく入るときと同じ）
- **暦のずらし方**: 入る市場の「全社が営業済みの日付」の次の日から営業する。会社の中の日付の値（キーが day・…Day のもの。0以下の印は除く）と、日にちごとのシフトのキーを同じ日数だけずらす。1日の最高記録など日付でない …Day の値はずらさない
- 元の市場では「移った」になる（記録・称号は残る。D1 の `market_companies` も `moved`）。移った会社・引退した会社は、1人が持てる会社（5社）の数に入らない
- **引退**: 終わった市場の会社か、破産した会社だけ（競争期間中の営業している会社は引退できない）
- 競争期間が終わった市場は、1人が作れる市場（5つ）の数に入れない
- 終わった市場でも端末で1日ずつ営業できる（日の確かめ方は同じ）。0時の同期・ランキングの集計には入らない
- **大会の称号**: 競争期間の最後の日の同期のあと、その市場の累計（競争期間全体）の総合評価で上位3位までのプレイヤー企業に「🏆 市場名 優勝」「🥈 準優勝」「🥉 3位」。AI 企業が上位でも順位はそのまま（週・月・年の称号と同じ）。総合評価が同じなら同じ順位。企業ごとに1つ（二度は渡さない）。
  最後の日に誰も営業せず同期がなかった市場は、終わって1日たってから毎日の定時の処理（JST 1:30）で渡す（終わって7日まで）
- 公開の一覧: 公開で、終わる前で、プレイヤー企業の数が上限より少ない市場を新しい順に50件。招待コードなしで入れるのは公開の市場だけ
- 制限: 持っていく途中でサーバーの処理が止まると（元の市場から出したあと、入る市場で受け取る前）、会社が元の市場で「移った」のまま残ることがある。戻す管理用の操作はまだない

### 測定（2026-11-04。この開発環境の Node.js）

| 計算 | 値 |
| --- | --- |
| 端末から届いた1日を確かめる（verify＋受け取り） | 約0.13ミリ秒/日 |
| 0時の同期の自動営業（店長の営業＋AI の判断＋次の日の朝） | 約0.65ミリ秒/社・日（5社×300日＝1,500社・日で約1.0秒。1回の要求で3,000社・日まで、残りはアラームで続ける） |
| 市場の状態 | 6社・300日で約63万文字（企業1社 約7.8万文字。直近60日の日報だけを持つ） |

E2E では、端末で実際に1日を営業して送った日が、受け取らない理由も順位から外す理由もなく受け取られることを確かめた（iPhone・PC）。

### 決めた細部（判断の範囲内での既定）

- 日と日の間の会社の状態は「その日の仕込み」（工事の日は精算済み）。端末は「翌日の仕込みへ」のあとの状態を送る
- 0時の同期のあと、営業中だった端末は、サーバーの状態（自動営業で進んだ分を含む）を読み直してから次の日を始める（状態の版で確かめる）
- サーバーの市場の画面からの経営の操作（方針・人・出店など）は、端末で営業中・同期中は断る。拡張の工事は端末の営業（閉店後）でだけ決める（工事の日の扱いを手動と同じにするため）
- 自動営業の日は、プレイヤーがいる店は店主（能力 0.65）が方針の値段で営業する。手動で決めた値段・発注の設定は残る
- 自動営業で期限を過ぎた未払金を払えないときは、今までどおり緊急の融資を受ける（Phase 3 で「借入の許可」の方針に置き換える。初期値は許可しない）

### Phase 3 で決めた細部（判断の範囲内での既定）

- 疲れが回復するように、社員にも休みの曜日を決められるようにした（今までは毎日全時間）。休みの日は日給なし。店長の休みの日は店長がいない日
- 満足度が「とても低い」（0.35未満）と、毎朝少しの確率で辞める。解雇ではないので解雇手当はない
- 自動営業の当日欠勤・遅刻は、確率の見込みで人手を減らす（乱数で引かない。同じ状態なら同じ結果）
- 自動営業の日のランダムイベントは、細かいシミュレーションの平均に合わせた式に含まれる（日ごとの抽選はしない）
- 赤字のときの対応の初期値は「3日続けて赤字なら広告と短期バイトを止める」（保守的）
- 株式発行・企業買収・営業時間の短縮は機能がないので、方針の画面では「しない」と表示する

## 9. ランキングの種別と集計（Phase 4。オーナーの判断 3a・3b・6）

数値はすべて、0時の同期でサーバーが確定した日（`company_periods`。上限を超えた日は数えない）から作る。端末の申告は使わない。

| 種別 | 計算 | コミュニティ内 | 全体 |
| --- | --- | --- | --- |
| 総売上・営業利益・最終利益 | 期間の純売上・営業利益・最終利益 | 合計 | ゲーム内の1日あたり |
| 顧客満足度 | 満足度の合計 ÷ 人数（手動で営業した日だけに値がある） | 同じ | 同じ |
| 企業価値成長率 | (期間の終わりの企業価値 − 始め) ÷ max(\|始め\|, 初期資金30万円)。企業価値は純資産（現金 − 借入の残り − 未払金 ＋ 設備の売却価値 ＋ 在庫の価値）なので、借入で水増しできない | 同じ | 同じ |
| 市場シェア | 純売上 ÷ 同じ期間の市場全体の純売上 | 同じ | 同じ（自分のコミュニティの中のシェア） |
| 従業員満足度 | 全店の従業員の満足度の平均（1日ごとの値の平均） | 同じ | 同じ |
| 店舗品質 | 店ごとに「評判÷5」「設備の状態の平均」「清潔さ（1 − 席と厨房の汚れ）」を同じ重みで平均し、全店で平均 | 同じ | 同じ |
| 総合評価 | 上の8種別の順位を同じ重みで平均（値のない種別は最下位として数える） | 同じ | 同じ |

- 期間: 週（JST の月〜日）・月・年・累計。`rank_agg` は企業 × 期間のキーごとに、0時の同期のたびにその企業の行から作り直す（`INSERT OR REPLACE … SELECT`。同じ期間を二度書いても同じ値で、二重に数えない）
- 全体ランキングは「新規の企業だけ」と「育てた企業も可」の2つに分け、数分だけ Worker のキャッシュに置く（D1 の読み出しを減らす）
- 報酬は称号（経済的な効果はない）。コミュニティ内は、その期間の最後の日の同期のあとに総合評価の上位3社（プレイヤー企業）へ。
  全体は毎日 JST 1:30 の定時の処理で、昨日で終わった期間の上位3社へ。`reward_key` で一意（同じ順位で二度は受け取らない）
- 前の期間との順位の変動を出す（前の期間に記録がなければ「初」）

## 10. 不正対策（仕様書 7 章）の対応

| 仕様書の項目 | 対応 |
| --- | --- |
| 架空売上・二重計上の防止 | 日報の売上は売上の取引と同じでなければ順位から外す。お金は取引の合計と同じでなければ受け取らない。集計は期間ごとに作り直すので二重に数えない |
| 関連企業間の不自然な取引の監視 | 企業間の取引の機能がまだない（Phase 5・6 の買収などと合わせて足す） |
| 不自然な価格操作の検知 | 値段が平均で定価の0.6倍未満・2倍超の日を監査記録に残す（受け取りには影響しない） |
| 借入による企業価値の水増し対策 | 企業価値は純資産（借入の残りを引く） |
| ランキング報酬の二重受領防止 | reward_key で一意（INSERT OR IGNORE） |
| クライアント側の進行日数改ざん防止 | 日の始めの条件（token）はサーバーが渡し、1回の送信で1日だけ。日付・日報の書き換えは受け取らない |
| 自動営業の二重実行防止 | 同期は企業ごとの済んだ日付から続きを計算する（二度呼んでも進みすぎない） |
| 同期中の競合更新防止 | 0時の計算中は、日の始め・経営の操作を断る |
| 企業・アカウント関係の不正検知 | 1つの市場に1人1社。1人5社まで。それ以上（別のアカウント同士の関係）は IP などの個人情報を持たないため見ていない |

検知だけで BAN はしない（監査記録の種類: market_day_rejected・market_day_flagged・market_day_expired・market_day_watch）。
