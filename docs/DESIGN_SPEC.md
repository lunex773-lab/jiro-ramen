1. ゲームの基本コンセプト

1.1 ゲーム概要

プレイヤーが小さな次郎系ラーメン店を経営し、実際に店内を歩き回り、食材の仕込み、ラーメン調理、注文処理、接客、清掃、片付け、設備管理を行う。

営業利益を生み出し、設備の購入、従業員の雇用、店舗の拡張に再投資する。

経営が順調になれば大型店舗を運営できる。一方で、仕入れの失敗、客足の減少、設備故障、人件費の増加、食材廃棄などが重なると経営難に陥る。

最終的には、プレイヤーが現場作業を中心に運営する小規模店から、設備と従業員を活用して多数の客を処理する大型店へ成長させる。

1.2 中核となるゲーム体験

	1.	一人称視点で店内を移動する。
	2.	食材を仕込む。
	3.	客の注文を受ける。
	4.	麺をゆで、スープや具材を準備する。
	5.	客の希望に合わせてラーメンを完成させる。
	6.	ラーメンを提供する。
	7.	食器を回収し、洗浄する。
	8.	卓上や床を清掃する。
	9.	食材と設備の状態を管理する。
	10.	売上、原価、人件費、家賃などを管理する。
	11.	店舗レイアウトを変更する。
	12.	設備を購入して作業を効率化する。
	13.	従業員を雇用し、仕事を任せる。
	14.	評判を高め、常連客や行列を獲得する。
	15.	店舗を拡張して経営規模を拡大する。
	16.	最大4人で役割を分担し、共同経営する。

単なるメニュー選択式の経営ゲームにはしない。店舗内の作業そのものをゲームプレイとして成立させる。

2. プラットフォームと技術スタック

2.1 クライアント

	•	対応端末：iPhone
	•	エンジン：Unity
	•	描画：Universal Render Pipeline（URP）
	•	視点：一人称
	•	操作：仮想スティック＋タップ／長押し／ドラッグ
	•	3Dモデル：Unity対応の3Dアセット
	•	保存：ローカルセーブ＋必要に応じたCloudflare上のクラウドセーブ
	•	通信：WebSocketを用いたゲーム専用プロトコル
	•	基本モード：オフラインのシングルプレイ
	•	オンラインモード：最大4人の共同経営

最初から高品質な全店舗を制作しない。先にゲームシステムとグレーボックスで遊べる状態を作り、その後にビジュアル品質を引き上げる。

2.2 バックエンド

Cloudflareを中心に構築する。

Cloudflare Workers

担当機能：

	•	APIルーティング
	•	認証トークンの検証
	•	ゲームセッション作成・参加要求
	•	セーブデータの読み書き制御
	•	リクエスト検証
	•	レート制限
	•	ゲームバージョンの確認
	•	プレイヤーの権限確認
	•	ログの記録
	•	データベースとストレージへのアクセス制御

Cloudflare Durable Objects

担当機能：

	•	共同経営ルームごとの接続管理
	•	最大4人の参加人数管理
	•	WebSocket接続
	•	プレイヤーの入退室
	•	共同経営状態の調整
	•	操作要求の検証
	•	同時操作の競合解決
	•	ゲーム状態の更新
	•	状態変更イベントの配信
	•	切断・再接続処理
	•	一時的なゲーム状態の復旧

原則として、1つの共同経営ルームにつき1つのDurable Objectを割り当てる。

ゲームルームIDからDurable Objectの識別子を決定し、同一ルームの状態更新が複数の独立したインスタンスに分散しない構成とする。

Cloudflare D1

担当機能：

	•	プレイヤープロフィール
	•	セーブスロットのメタデータ
	•	セーブデータのバージョン情報
	•	ゲーム進行の参照情報
	•	ルーム作成・終了記録
	•	プレイヤー別の実績
	•	不正操作・重要イベントの監査記録

D1をリアルタイムの全フレーム状態同期に使用しない。

Cloudflare R2

担当機能：

	•	大容量セーブスナップショット
	•	セーブデータの世代バックアップ
	•	必要に応じたリプレイや診断データ
	•	将来的なユーザー生成コンテンツ

小さなメタデータはD1、大きなスナップショットはR2に保存する。

Cloudflare KV

必要性を確認した場合に限り、次の用途で利用する。

	•	公開設定
	•	更新頻度が低いゲーム設定
	•	キャッシュ可能な読み取りデータ

資金、在庫、給与、破産状態などの重要データの唯一の保存先にはしない。

2.3 Cloudflareだけで実装する場合の技術的制約

Workersは一般的なUnity専用ゲームサーバーの実行環境ではない。

そのため、次の設計を採用する。

	•	ゲームシミュレーションをイベント駆動型にする。
	•	物理演算を毎秒数十回、サーバー側で完全再現する設計を避ける。
	•	クライアントから操作要求を受け取り、サーバー側で有効性を判定する。
	•	サーバーが確定したゲームイベントを各参加者へ配信する。
	•	重要な経済状態はサーバー側のルールでのみ変更する。
	•	クライアントの表示用アニメーションや補間は端末側で行う。
	•	Durable Objectsの実行時間、CPU制限、メモリ、接続維持、料金を検証する。
	•	WebSocket切断時に、未保存状態を失わない設計とする。

WebSocketの接続調整とイベント同期が可能であることは、Unityの標準的なNetcodeをそのまま動作させられることを意味しない。Unity側の通信層は独立したアダプターとして実装する。

技術検証で確認する事項

	1.	iPhone実機からCloudflare WebSocketへ接続できること。
	2.	最大4クライアントが同一ルームに参加できること。
	3.	連続したプレイヤー移動と操作イベントが処理できること。
	4.	状態同期が遅延や重複に耐えられること。
	5.	Durable ObjectsのCPU制限内で動作すること。
	6.	セーブデータをD1/R2へ安全に保存できること。
	7.	切断・再接続時に二重購入や二重売上が発生しないこと。
	8.	想定プレイ時間での料金を実測・推定できること。

検証が成立しない場合は、ゲーム本体のロジックを変更せずに通信アダプターを交換できる構造を維持する。

3. アーキテクチャと責務分離

次のモジュールを独立させる。

	•	Core：共通型、ゲーム状態、時間、乱数
	•	Interaction：調べる、持つ、置く、使用する
	•	Player：移動、視点、操作入力
	•	Cooking：麺、スープ、具材、調理工程
	•	Order：注文受付、注文キュー、提供判定
	•	Customer AI：客の意思決定、待機、移動、満足度
	•	Navigation：経路探索、通行可能判定
	•	Inventory：食材、在庫、仕込み、発注
	•	Cleaning：食器回収、洗浄、店内清掃
	•	Equipment：機材、故障、修理、稼働状態
	•	Employee AI：従業員の行動計画、担当、優先順位
	•	Economy：売上、原価、給与、家賃、維持費
	•	Reputation：評判、口コミ、来客需要、常連客
	•	Layout：店舗配置、購入、拡張、配置検証
	•	Career：キャリア進行、解放要素、目標
	•	Save：保存、復元、スロット管理
	•	Networking：接続、ルーム、同期、再接続
	•	Backend API：認証、セーブ、セッションAPI
	•	UI：HUD、メニュー、経営画面、警告
	•	Audio：環境音、調理音、客の声、通知
	•	Analytics：任意の診断・匿名化されたクラッシュ情報

ゲームルールをMonoBehaviourやUIに直接埋め込まない。経済計算や調理判定などの主要ロジックは、可能な限りUnityシーンに依存しないC#コードにする。

4. ゲーム進行

4.1 基本サイクル

	1.	店舗準備
	2.	仕込み
	3.	設備と在庫の確認
	4.	開店
	5.	客の来店
	6.	注文・調理・提供
	7.	食器回収・洗浄・清掃
	8.	食材切れや設備故障への対応
	9.	閉店
	10.	売上と支出の精算
	11.	経営状況の確認
	12.	設備購入・雇用・店舗拡張
	13.	次の営業日

プレイヤーは営業中にも作業を続ける必要がある。経営メニューだけで一日が完結する設計にはしない。

4.2 キャリア制

序盤：

	•	小さな店舗
	•	少ない設備
	•	少ない座席
	•	少ない仕込み量
	•	原則としてプレイヤー自身が主要業務を担当

中盤：

	•	設備追加
	•	座席追加
	•	店内拡張
	•	従業員の採用
	•	作業分担の最適化
	•	来客数の増加
	•	在庫と資金管理の複雑化

終盤：

	•	大型店舗
	•	複数の従業員
	•	高い来客処理能力
	•	多数の設備
	•	故障・衛生・人員配置の高度な管理
	•	最大4人での共同経営

進行はプレイヤーの判断と営業結果によって変化させる。

6. 本格的な調理システム

6.1 調理工程

ラーメン1杯は複数の工程で構成する。

	•	注文の確認
	•	麺の選択
	•	麺ゆで
	•	スープ準備
	•	タレの投入
	•	背脂などの準備
	•	豚・野菜などの具材準備
	•	麺の湯切り
	•	盛り付け
	•	オーダー内容との照合
	•	提供

工程ごとに作業時間、必要設備、必要材料、品質への影響を定義する。

6.2 注文内容

注文データには次を含める。

	•	麺量
	•	味の指定
	•	野菜量
	•	ニンニク量
	•	背脂量
	•	その他解放済みトッピング
	•	特殊な注文条件

メニューのバリエーションをデータとして管理し、新メニュー追加で調理コード全体を書き直さなくて済む構造にする。

6.3 調理品質

品質は次の要素から算出する。

	•	麺のゆで時間
	•	スープ温度
	•	具材の品質
	•	注文との一致
	•	調理工程の順序
	•	盛り付け
	•	提供時の温度
	•	食材の鮮度

調理品質は客満足度、口コミ、リピーター率に影響する。

完全な物理・化学シミュレーションではなく、ゲームとして納得できる因果関係を優先する。

6.4 失敗とリカバリー

	•	麺のゆですぎ
	•	材料不足
	•	注文の取り違え
	•	盛り付けミス
	•	調理中の放置
	•	食材の鮮度低下

失敗には時間、原価、客満足度への影響を設定する。

ミスが発生した場合でも、再調理や注文修正によるリカバリーを可能にする。

7. 客のAIシミュレーション

7.1 客の基本状態

客は次の状態を遷移する。

	•	来店候補
	•	入店
	•	行列参加
	•	着席待ち
	•	着席
	•	注文待ち
	•	注文済み
	•	調理待ち
	•	食事中
	•	退店準備
	•	退店
	•	クレーム対応
	•	途中退店

各状態の遷移条件は明示する。

7.2 客の個性

客データには次を持たせる。

	•	待ち時間への耐性
	•	価格への敏感さ
	•	味への評価傾向
	•	接客への敏感さ
	•	食事速度
	•	注文の複雑さ
	•	清潔さへの要求
	•	口コミ投稿傾向
	•	常連化しやすさ
	•	クレーム発生傾向

個性は固定的なラベルだけでなく、数値パラメータとして表現する。

7.3 行列

行列は店舗の需要と処理能力から発生する。

考慮する要素：

	•	店舗の評判
	•	時間帯
	•	過去の営業成績
	•	価格
	•	座席数
	•	注文処理能力
	•	調理時間
	•	従業員数
	•	店舗の混雑
	•	店外の待機人数

行列が長すぎると待ち時間への不満、途中離脱、口コミ悪化が発生する。

7.4 常連客

常連客は過去の来店と満足度に基づいて形成する。

保存対象：

	•	来店履歴
	•	注文傾向
	•	累積満足度
	•	最終来店日
	•	常連度
	•	店舗への評価

常連客は安定した需要を生み出すが、品質や接客が悪化すれば来店頻度が低下する。

7.5 口コミと評判

口コミは、単なるランダムな売上ボーナスにしない。

評価要因：

	•	味
	•	提供速度
	•	接客
	•	店内の清潔さ
	•	注文ミス
	•	品切れ
	•	価格と満足度のバランス
	•	設備や座席の快適さ

口コミは一定期間の集計を通して評判に反映する。

評判は将来の来店需要に影響する。短期的な売上増加と長期的な信用の間にトレードオフを設ける。

8. 食材・在庫・仕込み

8.1 在庫管理

食材ごとに以下を保持する。

	•	食材ID
	•	保有数量
	•	保管上限
	•	仕入れ単価
	•	仕入れ先
	•	仕入れ時間
	•	鮮度
	•	使用期限
	•	保管場所
	•	仕込み状態
	•	廃棄量

8.2 仕込み

仕込みには次の要素を持たせる。

	•	必要食材
	•	必要時間
	•	必要設備
	•	完成数量
	•	品質
	•	保管期限
	•	担当者
	•	中断可能かどうか

仕込み量を増やせば営業中の作業が減る一方、余らせると廃棄リスクが高くなる。

8.3 食材切れ

注文処理時に必要な食材が不足している場合、在庫を超えて消費させない。

対処方法：

	•	仕込み
	•	追加発注
	•	一部メニューの一時停止
	•	客への説明
	•	注文変更
	•	代替材料が許可された場合の変更

品切れを繰り返すと客満足度と評判が低下する。

8.4 食材消費の権限

マルチプレイでは、在庫消費はサーバー側で確定する。

クライアントが「食材を使った」と通知するだけで在庫が減る設計にはしない。

サーバーは操作の妥当性、数量、作業状態を検証し、同一材料の二重消費を防ぐ。

⸻

9. 食器回収・洗浄・清掃

9.1 食器

食器は状態を持つ。

	•	使用可能
	•	客が使用中
	•	回収待ち
	•	回収済み
	•	洗浄中
	•	洗浄済み
	•	破損

使用可能な食器が不足すると、着席や注文処理が制限される。

9.2 清掃

清掃対象：

	•	テーブル
	•	カウンター
	•	床
	•	洗い場
	•	ゴミ
	•	汚れた設備
	•	その他の解放済み清掃対象

清掃の必要度を数値化する。

汚れが蓄積すると衛生評価と客満足度が下がる。

9.3 忘れ物

客が退店するとき、一定確率で忘れ物イベントが発生する。

忘れ物には次を設定する。

	•	対象物
	•	発生場所
	•	発見状態
	•	放置時間
	•	対応方法

適切に保管・対応した場合、客満足度や評判が改善する場合がある。

忘れ物を放置した場合、店舗の対応評価に影響する。

実際のプレイヤーや参加者の個人情報をゲーム内の忘れ物として表現しない。

状態例：

11. 店舗レイアウト：ハイブリッド配置

11.1 基本方針

基本はグリッド配置とし、一部の設備・装飾は細かな位置・角度調整を許可する。

完全自由配置だけに依存しない。経路探索、当たり判定、iPhoneでの操作性、ネットワーク同期の複雑さを抑えるためである。

11.2 配置ルール

	•	設備の移動
	•	設備の回転
	•	グリッドへのスナップ
	•	対応対象の自由な微調整
	•	設置可能範囲の表示
	•	配置プレビュー
	•	配置確定
	•	取消し
	•	重複判定
	•	壁との干渉判定
	•	通路幅の判定
	•	客や従業員の通行可能性の判定
	•	設備へのアクセス可能性の判定

11.3 ハイブリッド配置の詳細

グリッド対象

大型調理設備、冷蔵庫、洗浄設備、カウンターなど。

微調整対象

椅子、装飾、小型の一部設備など。

自由調整対象でも、衝突判定や移動可能範囲を無視して配置できるようにはしない。

11.4 配置変更のタイミング

基本的に閉店後または準備時間に行う。

営業中の配置変更は原則禁止する。将来、営業中に移動可能な装飾などを導入する場合は、対象を個別に許可する。

11.5 動線の影響

設備配置は次の性能に影響する。

	•	プレイヤーの移動時間
	•	従業員の移動時間
	•	食材搬送時間
	•	調理時間のうち移動が占める時間
	•	客の着席効率
	•	清掃効率
	•	食器回収効率
	•	通路の混雑

設備の性能が同じでも、配置によって実際の処理能力が変化する設計にする。

11.6 配置データ

レイアウトデータには以下を含める。

	•	店舗区画ID
	•	オブジェクトID
	•	設備・装飾の種類
	•	位置
	•	回転
	•	微調整オフセット
	•	配置バージョン
	•	所有状態

ネットワーク上では、検証済みの配置変更だけを確定する。

12. 店舗拡張

12.1 基本進行

小さな店舗から開始し、利益を蓄積して拡張する。

拡張段階の例：

	1.	小規模店舗
	2.	拡張店舗
	3.	中規模店舗
	4.	大型店舗

段階名や数値はデータ化し、後から追加できるようにする。

12.2 拡張で解放されるもの

	•	床面積
	•	座席数
	•	厨房スペース
	•	設備設置可能数
	•	食材保管容量
	•	従業員の担当領域
	•	客の処理能力
	•	新設備
	•	新メニュー
	•	新しい経営目標

12.3 拡張費用

拡張には次のコストを設定する。

	•	工事費
	•	設備移設費
	•	休業による機会損失
	•	維持費増加
	•	必要な最低資金
	•	必要なキャリア条件

拡張すれば自動的に利益が増えるのではなく、需要と運営能力が伴わなければ赤字になる。

12.4 開発初期の実装方法

最初はあらかじめ定義した拡張区画を順に開放する。

その後、区画内のレイアウト自由度を高める。

初期から完全な建築エディターを作ることは避ける。

13. 従業員の採用・給与・AI

13.1 従業員の職種

	•	調理担当
	•	接客担当
	•	清掃・食器回収担当
	•	将来追加可能な専門職

従業員は職種に応じた仕事を行う。

13.2 従業員の能力

	•	作業速度
	•	調理技術
	•	接客態度
	•	衛生意識
	•	移動効率
	•	勤務安定性
	•	経験値
	•	給与
	•	疲労や勤務状態（導入する場合）

安い従業員を一律に無能にしない。個々の能力と給与にトレードオフを持たせる。

13.3 従業員AIの基本構造

従業員AIは、以下の構造を採用する。

	1.	仕事候補の取得
	2.	優先度計算
	3.	担当範囲の確認
	4.	経路探索
	5.	移動
	6.	作業実行
	7.	結果確認
	8.	次の仕事へ移行

単純なランダム行動ではなく、状況に応じて仕事を選択する。

13.4 タスク優先度

初期優先順位の例：

	1.	安全上の重大な問題
	2.	進行中の調理工程
	3.	注文提供に直結する仕事
	4.	食材補充
	5.	退席後の食器回収
	6.	テーブル清掃
	7.	洗浄
	8.	ゴミ処理
	9.	通常清掃

優先順位は職種・能力・担当設定によって変更可能とする。

13.5 二重割り当ての防止

同じタスクを複数の従業員が同時に実行しないよう、タスクの取得と予約を管理する。

マルチプレイではタスクの確定をサーバー側で行う。

作業途中で担当者が離脱した場合、タスクを解放して他の従業員が引き継げるようにする。

13.6 従業員の雇用

採用時に次を確認できる。

	•	給与
	•	能力
	•	職種
	•	経験
	•	採用費
	•	勤務条件

採用は店舗の資金から支払う。

13.7 給与と解雇

給与は営業日単位で精算することを基本とする。

資金不足時は以下を可能にする。

	•	設備購入の延期
	•	仕入れ量の調整
	•	無駄な支出の削減
	•	営業体制の見直し
	•	従業員の解雇
	•	店舗拡張の延期

解雇には必要に応じて費用や一時的な処理能力低下を設定する。

従業員を増やせば人手不足は解消しやすくなるが、給与が増えるため利益を圧迫する。

14. 経済システム

14.1 基本計算

営業日の営業利益は、次を基本とする。

営業利益
= 売上

	•	食材原価
	•	人件費
	•	家賃
	•	設備維持費
	•	光熱費等の営業費
	•	修理費
	•	その他の費用

キャッシュフローと会計上の利益は区別する。

食材購入や設備購入は現金を減らす。食材を使用したときの原価計上と購入時の現金減少を混同し、二重計上しないようにする。

14.2 初期バランスの仮値

以下はゲームバランス調整用の初期案であり、実際の店舗の市場価格を表すものではない。

	•	初期資金：300,000円
	•	初期店舗：小規模
	•	採用費：20,000〜50,000円
	•	従業員の日給：12,000〜20,000円
	•	家賃：営業日あたり8,000〜15,000円
	•	設備費：設備ごとに設定
	•	食材原価：商品・食材ごとに設定

この数値をコード内に直書きしない。BalanceConfigなどのデータとして管理する。

14.3 売上

売上は実際に提供が完了した注文に対して計上する。

注文キャンセル、返金、作り直し、廃棄は別イベントとして記録する。

14.4 人件費

給与は契約条件と勤務状態に応じて計算する。

従業員の採用や解雇によって、その日の給与が不自然に消失したり二重計上されたりしないよう、給与計算期間を明示する。

14.5 設備投資

設備購入では次を考慮する。

	•	購入費
	•	設置可能面積
	•	作業短縮効果
	•	処理能力
	•	維持費
	•	故障率
	•	回収に必要な営業日数

高額設備を買うだけで常に正解になるバランスにしない。

14.6 経営ダッシュボード

最低限、以下を表示する。

	•	現在資金
	•	本日の売上
	•	本日の営業利益
	•	食材原価
	•	人件費
	•	家賃
	•	維持費
	•	修理費
	•	在庫不足
	•	廃棄
	•	来客数
	•	平均待ち時間
	•	客満足度
	•	評判
	•	翌営業日の予測支出

数値の根拠をプレイヤーが理解できるようにする。

15. 破産・ゲームオーバー

15.1 破産条件

ゲーム内の利用可能資金がなくなり、支払い義務を履行できず、定められた救済手段を使っても営業継続が不可能になった場合、破産判定を行う。

単に一時的に現金が少ないだけで即ゲームオーバーにしない。

15.2 破産前の警告

資金が危険水準に達したら、段階的に通知する。

	•	資金注意
	•	次回支払額の警告
	•	支払い不足の予測
	•	緊急の支出見直し
	•	支払期限超過
	•	破産判定

警告には金額と原因を表示する。

15.3 救済の機会

プレイヤーには、破産前に支出削減や解雇などの選択肢を与える。

融資を導入する場合は、借入額、利息、返済条件、利用制限を明示する。初期版では必須機能としない。

15.4 ゲームオーバー処理

破産時には次を実行する。

	1.	営業を停止する。
	2.	未完了タスクを安全に終了する。
	3.	資金・債務・原因を記録する。
	4.	結果画面を表示する。
	5.	再挑戦またはセーブ選択を提示する。

セーブデータを自動削除しない。

共同経営時は破産判定をサーバー側で確定し、全員へ同じ結果を配信する。

16. セーブデータ：3スロット

16.1 基本仕様

シングルプレイのセーブスロットを3つ用意する。

各スロットは独立したキャリアデータを持つ。

スロットには次を保存する。

	•	セーブID
	•	スロット番号
	•	データバージョン
	•	作成日時
	•	最終更新日時
	•	キャリア進行
	•	店舗区画
	•	店舗レイアウト
	•	設備
	•	従業員
	•	資金
	•	債務
	•	在庫
	•	仕込み
	•	評判
	•	常連客
	•	解放要素
	•	経営履歴
	•	ゲームオーバー状態

16.2 保存方式

ローカルセーブを基本とする。

クラウドセーブを導入する場合、Cloudflare側にスナップショットを保存できる構造にする。

クラウドセーブは、ローカルデータと競合した場合に無条件で新しい方を採用しない。更新バージョンと競合を検出し、ユーザーに選択肢を提示する。

16.3 保存の安全性

	•	保存中にアプリが終了しても破損しにくい方式を使う。
	•	保存データのバージョンを持つ。
	•	読み込み時にスキーマ検証を行う。
	•	保存前に重要データの整合性を確認する。
	•	破損時にバックアップから復旧できるようにする。
	•	スロット削除と上書きには確認を設ける。
	•	ゲームオーバー後もデータを保持する。

16.4 マルチプレイのセーブ規則

共同経営は、ホストが所有するキャリアを基準とする。

参加者の個人セーブを共同経営の進行で上書きしない。

共同経営終了時は、権限を持つホストが保存処理を要求し、サーバー側で状態を検証した後に確定する。

同時保存、切断、二重要求を処理できるよう、保存要求に一意のIDとバージョンを付ける。

17. 最大4人のオンライン共同経営

17.1 確定仕様

	•	最大4人
	•	共同経営のみ
	•	全員で同一店舗を運営
	•	別店舗を個別経営するオンラインモードは実装しない
	•	資金、在庫、設備、客、注文、評判を共有
	•	プレイヤーは同時に店内を移動できる
	•	役割分担を自由に変更できる

17.2 役割例

	•	調理
	•	注文受付・提供
	•	仕込み・在庫
	•	清掃・食器回収
	•	店舗経営・設備管理

役割は固定クラスではなく、プレイヤーの行動や担当設定によって切り替えられる。

17.3 共有状態

	•	店舗資金
	•	売上
	•	在庫
	•	食材消費
	•	調理工程
	•	注文状態
	•	客の状態
	•	客の位置
	•	座席状態
	•	設備の状態
	•	店内の汚れ
	•	従業員の状態
	•	店舗レイアウト
	•	評判
	•	常連客
	•	ゲーム内時間
	•	営業日
	•	破産状態

17.4 権威モデル

サーバー権威型の状態管理を採用する。

Cloudflare Durable Objectが、ルーム内の重要な状態遷移を検証・確定する。

クライアントは操作要求を送る。クライアントが直接、資金や在庫の最終値を決定してはならない。

ただし、Durable ObjectsはUnityの完全なゲーム物理サーバーではない。クライアント側で行う描画・補間・局所的な演出と、サーバー側で確定する経営・操作状態を明確に分ける。

17.5 同期方式

プレイヤー移動

	•	入力や移動状態を通信する。
	•	他プレイヤーの表示は補間する。
	•	移動可能範囲と速度を検証する。
	•	クライアントの位置を無条件に信用しない。
	•	更新頻度は実機・通信試験で決める。

初期検証では毎秒10〜20回程度の位置更新を候補とし、必要性とCloudflareの制限を測定する。これは確定値ではない。

ゲームイベント

次のイベントは確定後に同期する。

	•	注文受付
	•	調理工程の開始・完了
	•	食材消費
	•	ラーメン提供
	•	売上計上
	•	食器回収
	•	清掃完了
	•	設備故障
	•	設備修理
	•	従業員タスクの割り当て
	•	設備購入
	•	レイアウト変更
	•	店舗拡張
	•	給与支払い
	•	破産判定

同時操作の競合

例：2人が最後の豚肉を同時に取ろうとした場合

	1.	それぞれの操作要求を受け取る。
	2.	要求の形式と権限を検証する。
	3.	現在の在庫と状態を確認する。
	4.	先に有効に確定した要求を処理する。
	5.	後続の要求は在庫不足として拒否する。
	6.	結果を全参加者へ配信する。

二重消費、二重購入、二重売上を発生させない。

17.6 イベントの信頼性

各操作要求には次を持たせる。

	•	requestId
	•	roomId
	•	playerId
	•	eventType
	•	対象ID
	•	必要な引数
	•	クライアントが観測した状態バージョン

サーバーは重複要求を識別し、同一要求を二度適用しない。

クライアントの時刻だけで注文や経済処理の順序を決めない。サーバー側の順序番号または状態バージョンを利用する。

17.7 再接続とホスト切断

共同経営の状態はホスト端末だけに依存させない。

	•	切断したプレイヤーは再接続できるようにする。
	•	再接続時に現在の確定状態を再送する。
	•	重複イベントを再適用しない。
	•	ホストが切断した場合も、確定済みの状態を失わない。
	•	ホスト切断時に、サーバー側の状態が復元できない場合はセッションを安全に一時停止する。
	•	復元できない状態を推測で続行しない。

初期版では、ホストが切断しても他プレイヤーだけで無条件に経営を続行する設計にしない。セッション一時停止と再開を優先し、ホスト移行は別途検証後に追加する。

17.8 店舗編集の競合

複数人が同時に設備を配置変更しないようにする。

	•	配置要求はサーバーで検証する。
	•	設置可能範囲を確認する。
	•	資金を確認する。
	•	重複や通路閉塞を検証する。
	•	変更を一意に確定する。
	•	結果を全員へ配信する。

初期版では閉店後または準備時間のみ配置変更を許可する。

18.3 セキュリティ

	•	認証情報をクライアントに埋め込まない。
	•	APIキーや秘密鍵をリポジトリに保存しない。
	•	入力値をサーバーで検証する。
	•	参加人数をサーバー側で制限する。
	•	不正なルームIDや権限のない操作を拒否する。
	•	接続・操作のレート制限を設ける。
	•	セーブデータのアクセス権限を検証する。
	•	機密情報をログに記録しない。
	•	セッション参加用トークンには有効期限を設ける。
	•	通信切断時に二重処理が発生しないようにする。
	•	サーバーの確定状態をクライアントから直接上書きさせない。

18.4 セーブの耐久性

Durable Objectのメモリ上の状態だけを永続データとして扱わない。

重要なチェックポイントで確定状態を保存する。保存の頻度は料金、応答性、復旧時の損失範囲を比較して決める。

セッション中の一時状態と、復旧に必要な確定状態を分離する。

22. 必須テスト項目

経済

	•	売上が二重計上されない。
	•	食材原価が二重計上されない。
	•	給与が二重支払いされない。
	•	設備購入時に資金が正しく減る。
	•	修理費が正しく計上される。
	•	破産判定が全員で一致する。

在庫

	•	在庫以上に食材を消費できない。
	•	同時操作で在庫がマイナスにならない。
	•	仕込み数量が正しく反映される。
	•	廃棄と消費を区別できる。

従業員

	•	同じタスクを無制限に二重実行しない。
	•	通路が塞がれている場合に停止状態を検知する。
	•	担当者が離脱したタスクを再割り当てできる。
	•	従業員数が増えたときに処理負荷を測定できる。

レイアウト

	•	設備が壁や他の設備に重ならない。
	•	通路が完全に塞がれない。
	•	客と従業員が必要な場所へ到達できる。
	•	マルチプレイ中に不正な配置を確定できない。

セーブ

	•	3スロットが互いに独立している。
	•	上書きで別スロットが壊れない。
	•	保存中の終了で破損しにくい。
	•	古いデータの読み込み処理がある。
	•	破損データの検出と復旧手順がある。

マルチプレイ

	•	最大4人を超えて参加できない。
	•	同じ要求を再送しても二重処理されない。
	•	接続切断で資金や在庫が不整合にならない。
	•	再接続時に状態を復元できる。
	•	同時調理、同時購入、同時配置変更を処理できる。
	•	ホスト切断時に確定済み状態が失われない。
	•	サーバーからの確定状態とクライアント表示が最終的に一致する。

24. 最終的な設計原則

本プロジェクトで最も重要なのは、見た目だけを先に作ることではなく、経営・調理・客・従業員・店舗拡張・マルチプレイが相互に影響するゲームを成立させることである。

特に次の原則を守る。

	1.	実際の作業がゲームプレイになること。
	2.	利益を出して再投資する経営サイクルが成立すること。
	3.	従業員を雇うことで処理能力が増える一方、給与負担も増えること。
	4.	店舗レイアウトが実際の動線と処理能力に影響すること。
	5.	客の個性・接客・品質・清潔さが評判に反映されること。
	6.	資金難は予兆を示した上で、経営判断の結果として破産に至ること。
	7.	3つのセーブデータを安全に管理すること。
	8.	最大4人が同じ店舗を共同経営できること。
	9.	Cloudflareの制約を無視せず、実際に動く通信方式を採用すること。
	10.	重要なゲーム状態をクライアントだけで確定させないこと。
	11.	グレーボックスから開始し、段階的に品質を上げること。
	12.	実装・ビルド・テスト・検証の完了を確認してから次の工程へ進むこと。

25. Claude Codeで最初に実行する作業

この設計書を受け取ったら、直ちに全機能を一括実装してはならない。

最初に次の作業だけを行う。

	1.	既存リポジトリを調査する。
	2.	現在のプロジェクト構造を報告する。
	3.	UnityとiOSの開発環境を確認する。
	4.	Cloudflareの利用可能な機能と制約を公式ドキュメントで確認する。
	5.	WebSocketとDurable Objectsによる4人共同経営の技術検証計画を作成する。
	6.	各Phaseの依存関係を整理する。
	7.	最小限の実装計画と受け入れテストを提示する。
	8.	不明点、技術的リスク、追加費用が発生する箇所を明示する。

その後、Phase 0から順番に進める。

最優先の成果物は、iPhoneで一人称移動を行い、厨房の設備を操作し、ラーメンを1杯調理して客に提供できる、実際に遊べる最小プロトタイプとする。

そのプロトタイプが安定してから、経済、従業員AI、店舗拡張、Cloudflareバックエンド、4人共同経営へ拡張する。
