# 統合進化設計書 v2.1 — 実装計画

前提: `EVOLUTION_CURRENT_STATE_AUDIT.md`（現状）、`EVOLUTION_GAP_ANALYSIS.md`（差）、`ECONOMY_BALANCE_AUDIT.md`（経済）、`EVOLUTION_RISK_REGISTER.md`（リスク）。
各フェーズの完了条件を満たしてから次へ進む。各段階で変更したファイル・テストの結果・調整前後の数値・残りを記録する。
「（要確認）」はオーナーに決めてもらう点。

## 基本の考え方: 「独立したモードの集合」にしない最小の差分

今の `GameState` は「1つの店」の状態で、店の sim（客・調理・従業員・在庫・設備・日報）はすべてこれを読み書きしている。
これを壊さずに会社・複数店舗へつなぐため、

1. **今の `GameState` を「プレイヤーがいる店（店舗）」のまま使う**。店の sim 関数・描画・共同経営の差分配信は変えない
2. その上に **会社の層（`company`）を足す**。会社が持つもの: 名前・お金（今の `s.money` を会社のお金として扱う）・借入・店舗の一覧・会社の財務の履歴・成長段階
3. **2店舗目以降は「店舗の記録」として会社に持つ**。プレイヤーがその店に入るときは、今の店の状態を記録にしまい、その店の状態を取り出して `GameState` の店の部分に入れる（店を切り替えても会社のお金・履歴は同じ）
4. **プレイヤーがいない店は「店長の営業」で1日ずつ計算する**（下の Phase 2 の論点。推奨案）
5. 1店舗のうちは今と同じ画面・同じ遊び方。2店舗目を持ったら経営メニューに「会社」の画面が増える

これで、序盤の店・資金・評判・設備・従業員・日報はそのまま会社の1店舗目として引き継がれ、キャリアを作り直さない。

## Phase 2: 会社と複数店舗

| # | 作業 |
| --- | --- |
| 2-1 | 会社の層（`company`）と店舗の記録の型。セーブの `schema` を 2 に上げ、`migrate` で今のセーブを「会社＋1店舗目」にする（元のデータは残す・古いセーブを読むテスト） |
| 2-2 | 店舗別の日報と会社の集計（店舗の合計 = 会社、のテスト） |
| 2-3 | 2店舗目の出店（物件の候補・初期費用・解放の条件はデータ）。店の切り替え（店に入る・出る） |
| 2-4 | 店長と方針（通常営業・発注・修理費の上限・採用・価格・利益目標）。プレイヤーがいない店の営業 |
| 2-5 | 会社の画面（店舗一覧・店舗別損益・会社の財務・原因の説明）。1店舗のうちは今のまま |

**（要確認・最大の論点）プレイヤーがいない店の営業のしかた**
- 推奨: プレイヤーがいる店だけ今の細かいシミュレーション。ほかの店は店長の能力・従業員・設備・在庫・評判・方針から1日分を計算する。計算の式は、同じ条件の細かいシミュレーションの結果に合わせて調整し、差をテストで確かめる（iPhone でも軽い。共同経営のサーバーも軽い）
- ほか: すべての店を細かく動かす（重い）、閉店後にまとめて早送りで細かく動かす（待ち時間が出る）

## Phase 3: 共通市場と企業間競争（ひとりプレイの AI 企業から）

地域の需要・物件・人材・食材の市場、競合の店が来客に効く、市場シェア（直近30日の売上の割合、分母0なら0）、AI 企業（プレイヤーと同じ規則、意思決定の理由を記録）。
**（要確認）** 最初はひとりプレイで AI 企業と競う形から始め、オンラインで複数のプレイヤー企業が競う形は Phase 4 の時間管理のあとにする（推奨）。

## Phase 4: 継続型の経営（サーバーの時間管理）

市場ごとの権威オブジェクト、最終時刻から必要なイベントまでの時間差の処理、アラーム、二重実行の防止、不在中の自動運営の方針、不在中の報告。Cloudflare の料金・制限は公式の最新情報と実測で判断。

## Phase 5: 法人化・株式・企業価値

成長段階（法人化・株式会社化）の条件はデータ。株式数・持株比率・株式発行（希薄化）・企業価値（正規化した利益 × 評価倍率）・株価の更新のタイミング・式の版の保存。自由な株式売買は後回し。

## Phase 6: 買収・組織

不採算店舗の売却・閉鎖 → AI 企業への買収提案 → AI 企業からの提案 → プレイヤー企業間の合意型の買収。資産・負債・店舗・従業員・履歴の引き継ぎの整合をテストで。

## Phase 7: 実機・品質・運用

iPhone Safari 実機、長時間・長期不在、負荷試験、3D・音、セキュリティ、Cloudflare の費用、バックアップと復旧、App Store の調査。
