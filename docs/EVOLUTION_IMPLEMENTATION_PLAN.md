## 基本の考え方: 「独立したモードの集合」にしない最小の差分

今の `GameState` は「1つの店」の状態で、店の sim（客・調理・従業員・在庫・設備・日報）はすべてこれを読み書きしている。
これを壊さずに会社・複数店舗へつなぐため、

1. **今の `GameState` を「プレイヤーがいる店（店舗）」のまま使う**。店の sim 関数・描画・共同経営の差分配信は変えない
2. その上に **会社の層（`company`）を足す**。会社が持つもの: 名前・お金（今の `s.money` を会社のお金として扱う）・借入・店舗の一覧・会社の財務の履歴・成長段階
3. **2店舗目以降は「店舗の記録」として会社に持つ**。プレイヤーがその店に入るときは、今の店の状態を記録にしまい、その店の状態を取り出して `GameState` の店の部分に入れる（店を切り替えても会社のお金・履歴は同じ）
4. **プレイヤーがいない店は「店長の営業」で1日ずつ計算する**（下の Phase 2 の論点。推奨案）
5. 1店舗のうちは今と同じ画面・同じ遊び方。2店舗目を持ったら経営メニューに「会社」の画面が増える

これで、序盤の店・資金・評判・設備・従業員・日報はそのまま会社の1店舗目として引き継がれ、キャリアを作り直さない。

## Phase 3＋4: オンラインの共通市場と継続型の経営（オーナーの判断で一緒に進める）

- 市場ごとの権威オブジェクト（Durable Object。1つの市場の経済状態はこれだけが確定する）と、市場の時間（サーバーの時計。最終時刻から必要なイベントまで時間差で進める。アラームと、アクセス時の追いつきの二重実行を防ぐ）
- 企業の参加: 既存のキャリア（会社＋店舗）を市場へ移すときは、コピー・変換・規則への適合の確認をし、元のセーブを残す（設計書 6.1）
- 市場の中身: 地域の需要・物件・人材・食材、競合の店が来客に効く、市場シェア（直近30日の売上の割合、分母0なら0）
- AI 企業: プレイヤーと同じ規則、意思決定の理由を記録（ルールベース → 履歴に応じた戦略 → 競合への対応 → 出店・撤退 → 買収提案）
- プレイヤー企業は最大4社（初期の設計の上限）。不在中の店は店長の方針（Phase 2-4）で営業する
- Cloudflare の料金・制限は公式の最新情報と実測で判断する

## Phase 5: 法人化・株式・企業価値

成長段階（法人化・株式会社化）の条件はデータ。株式数・持株比率・株式発行（希薄化）・企業価値（正規化した利益 × 評価倍率）・株価の更新のタイミング・式の版の保存。自由な株式売買は後回し。

## Phase 6: 買収・組織

不採算店舗の売却・閉鎖 → AI 企業への買収提案 → AI 企業からの提案 → プレイヤー企業間の合意型の買収。資産・負債・店舗・従業員・履歴の引き継ぎの整合をテストで。

## Phase 7: 実機・品質・運用

iPhone Safari 実機、長時間・長期不在、負荷試験、3D・音、セキュリティ、Cloudflare の費用、バックアップと復旧、App Store の調査。
