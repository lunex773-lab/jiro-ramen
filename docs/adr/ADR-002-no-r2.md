# ADR-002: R2 を使わず、セーブ本体も D1 に置く

- 状態: 承認（2026-10-27 プロジェクトオーナーの指示「R2は使用せずにやりたい」）
- 関連: 設計書 2.2「大きなデータは R2、メタデータは D1」, 16.2, 18.4

## 背景

設計書はセーブのスナップショット本体を R2、メタデータを D1 に置くとしていた。
オーナーは R2 を使わない構成を希望した（R2 を使うにはダッシュボードでの有効化と、支払い情報の登録を求められることがある）。

## 決定

- クラウドセーブの本体（SaveFile の JSON）を D1 の `save_bodies` 表に置く。スロットごとに直近 3 世代を残す。
- 共同経営の保存の控え（ホストが保存したとき・ルームを終えたときの状態）を D1 の `room_snapshots` 表に置く。
  保存の控えは直近 3 件、ルームを終えたら最終状態だけを残し、30 日より古いものは消す。
- D1 の 1 行の上限（2,000,000 バイト）より少し小さい 1,900,000 バイトを本体の上限とし、超える場合は 413 を返す。
  通常のセーブは 20〜30KB 程度。
- 競合の扱い（revision による楽観ロック、409 で内容を見せて選ばせる）は変えない。
- 一度もデプロイしていなかったため、初期スキーマ（`migrations/0001_init.sql`）を書き換えた（`r2_key` 列を削除し、上の2表を追加）。

あわせて、D1 のテーブルは Worker が最初の要求で自分で作る（`src/schema.ts`）。
適用済みの記録は wrangler と同じ `d1_migrations` 表に残すので、`wrangler d1 migrations apply` と併用できる。
これにより、ダッシュボードの GitHub 連携（Workers Builds）でも、ビルド用 API トークンへの D1 権限の追加や
特別なデプロイコマンドが要らない。

## 影響

- Cloudflare 側で用意するものは D1 データベース 1 つと、秘密鍵 `SESSION_SECRET` だけになる。
- D1 の無料枠の容量（1 データベース 500MB。docs/CLOUDFLARE_SETUP.md）を、セーブ本体も使う。
  1 人 3 スロット × 3 世代 × 30KB ≒ 270KB なので、約 1,800 人分で 500MB に近づく。利用者が増えたら
  世代数を減らす・圧縮する・有料プランにする・R2 に戻す、のいずれかを検討する。
- R2 に戻す場合は、`api/saves.ts` と `room.ts` の保存先を差し替える（API の形は変わらない）。
