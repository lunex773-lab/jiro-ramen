# 営業改良: 差分分析（Phase 0）

設計書の要求と現状（`SALES_IMPROVEMENT_CURRENT_STATE.md`）の差分と、何を再利用して埋めるかをまとめます。
新しい仕組みは、既存の部品で足りないところだけに小さく足します。

## 共通イベント基盤

| 要求 | 現状 | 埋め方（再利用するもの） |
| --- | --- | --- |
| イベント定義・安定した ID | なし | イベントの種類 ID（`sns_buzz` など）は固定の文字列。発生ごとの ID は既存の `newId(s, 'ev')` |
| 発生条件・確率・クールダウン | 各処理で `rand(s)` | 数値は `BALANCE.events` に集約。最後に起きた日をイベントごとに記録して日単位のクールダウン |
| 発生中の状態・終了条件 | なし | 状態に `events`（JSON）を追加。古いセーブには無いので、読むときに既定値で補う（任意の項目にしてセーブ形式の版は上げない） |
| 再現できる抽選 | `s.rng` は 1 本 | **イベント専用の乱数** `events.rng`（シードから作る）を使い、イベントが起きない限り既存の乱数の並びを変えない |
| 二重発生の防止 | — | 抽選した日・発生中の ID を状態に記録し、同じ日に二度抽選しない |
| テスト用の強制発生 | — | core に `forceEvent(s, ctx, kind)`。ひとりプレイ専用の操作 `debugEvent`（共同経営のサーバーは受け付けない） |
| ロジックと演出の分離 | `emit` の仕組みがある | core は状態と `emit` のイベントだけを作り、演出（音・光・吹き出し）は client が読んで出す。演出が失敗しても状態は壊れない |
| セーブ・同期 | 状態は JSON で丸ごと保存・差分配信 | `events` も状態の一部なので、そのまま保存・同期される |
| 発生頻度の実測 | — | `events.stats` にイベントごとの抽選回数・発生回数を記録（爆発事故のリセットでも消さない） |

## A. SNS でバズる

| 要求 | 埋め方 |
| --- | --- |
| 低確率・評判や直近の評価を参照 | 営業中、一定間隔で抽選。確率 = 基本値 ×（評判/3）²×（直近の口コミの平均による倍率）。1 日 1 回まで、終わってから数日のクールダウン |
| 来客増加は実際の客・注文フローで | `arrivalRate` に倍率を掛けるだけ。売上を直接足さない。客は通常どおり並び、食券を買い、注文し、提供されたときに計上 |
| 混雑・遅延・ミスで評判が下がる／うまく回せばプラス | 既存の満足度・口コミ・常連化がそのまま効く。SNS を見て来た客は口コミを書きやすい（投稿する人たち） |
| スマホ・投稿・通知・来客増の表示 | 通知と上部の表示（残り時間）、SNS を見て来た客はスマホを手に持ち、一部が「SNSで見た」と話す |

## B. 怒った客・理不尽なクレーム

| 要求 | 現状 | 埋め方 |
| --- | --- | --- |
| 原因: 注文ミス・品質 | ある | 既存の判定に原因（`mistake` / `quality`）を記録 |
| 原因: 提供遅延 | なし | 着席後の待ちが我慢の限度に近づいたとき、確率でクレーム（提供前） |
| 原因: 店内の汚れ | なし | 汚れた席に座ったとき、確率でクレーム（提供前） |
| 原因: 客の性格・理不尽な要求 | なし | 良い丼を出しても、クレームを言いやすくマナーの悪い客がまれに理不尽な要求をする（店全体で間隔をあけ、1 日の上限あり） |
| 対応: 謝罪・作り直す・返金・説明・断る | 作り直す・返金のみ | 動詞を 3 つ追加（`complaint_apologize` / `complaint_explain` / `complaint_refuse`）。既存の 2 つの ID は変えない |
| 結果: 返金額・食材・時間・評判・満足度 | 作り直し・返金のみ | 対応ごとに所要時間・費用・満足度の変化を決める。断る・説明するで損失を抑えられる場合を作る（理不尽な要求のとき） |
| 提供前の返金 | — | 売上は提供時に計上するので、提供前の「返金」は食券の払い戻し（注文の取り消し、お金は動かない）。作り直しは提供後だけ |
| 同じクレームの連発防止 | なし | 1 回の来店でのクレームは 2 回まで、同じ原因は作り直しのあとだけ再発。失敗した対応は同じクレームの間は選べない |
| 従業員の対応 | 常に作り直す | 原因に合わせて選ぶ（遅延・汚れ → 謝る、理不尽 → 説明 → 断る、品質・ミス → 作り直す） |

## C. 有名レビュアー・覆面調査員

| 要求 | 埋め方 |
| --- | --- |
| 通常の客に混じって低確率で来店・正体は分からない | 開店時に抽選し、当たった日は営業中のある時刻以降に来た最初の新規客が調査員になる。見た目は普通（ときどきメモを取るだけ） |
| 評価項目は実際の営業状態から | 退店時の満足度の項目（味・速さ・接客・清潔さ・正確さ）をそのまま使う。運の要素は入れない |
| 一定時間後に公開 | 翌日の仕込みの開始時に公開（通知と、結果を知らせる画面） |
| 高評価: 評判上昇・新規客増 | 評判を直接少し上げ、数日間 来客の倍率を上げる |
| 低評価: 評判低下・一時的な客減・改善点の提示 | 評判を少し下げ、数日間 来客の倍率を下げ、点数の低い項目を改善点として示す |
| 通常客の流れを再利用 | 客そのものは通常の客（目印の項目が付くだけ）。食べずに帰った場合も評価する |

## D. 珍しい客

| 要求 | 埋め方 |
| --- | --- |
| D-1: 金髪の成人女性と彼氏のカップル | 2 人を続けて行列に並ばせる（`partyId`）。席は隣が空いていれば隣に座る。見た目を指定する項目（`look`）を客に足し、client の人物モデルに見た目の上書きを追加 |
| D-1: 彼氏との会話で一度だけ | 2 人が近くにいる（行列・待ち・席）ときに一度だけ吹き出しで話す。その後は通常の客 |
| D-2: 一人客が食事中に小声で一度だけ | 食事の途中で一度だけ、小さな吹き出しで話す。味に満足しているときだけ（セリフで利益は増やさない） |
| セリフはデータで管理 | `packages/core/src/data/events.ts` にセリフ・投稿文・クレーム文をまとめる |
| 発生率は設定値・同じ日に連発しない | `BALANCE.events.rare` で確率、1 日 1 回まで |
| 表示できなくても止まらない | 吹き出しは状態の `say` を表示するだけなので、画面外でも進行は止まらない |

## E. 爆発事故・探索・リセット

| 要求 | 現状 | 埋め方 |
| --- | --- | --- |
| 営業日単位で 0.001% | — | **開店（`openShop`）の時に 1 日 1 回だけ抽選**。当たったら、その日の営業中の時刻を決めて予約。抽選した日を記録し、同じ日に二度抽選しない |
| セーブ・ロードでの重複抽選 | — | 抽選は開店の操作の中だけ。開店後に保存して読み直しても再抽選しない |
| 異常 → 閃光・揺れ・音・暗転 → 壊滅 → 死亡の表示 → 気絶 → 時間経過 → 目覚め | — | core は「予兆」「壊滅」の 2 段階と経過時間だけを持つ。演出（閃光・揺れ・暗転・文字・目覚め）は client が経過時間を見て出す |
| 探索中は営業処理を止める | `step` は phase で止まる | 壊滅の間は `step` で営業処理をしない（事故の経過時間だけ進める）。操作は移動とリセットだけ受け付ける |
| 焼けた店内 | — | 既存の店・設備・椅子・丼のモデルを使い、材質を焦げた色に、椅子を倒し、丼を床に散らし、人物を倒れた姿勢に、煙・灰・残り火・火花、照明の点滅、不気味な環境音を足す。リセットで元に戻す |
| 「リセットする」ボタン（任意） | — | 目覚めたあと画面に表示。押すまで探索を続けられる |
| 仕込み開始時点の保存 | なし | **翌日へ進んで仕込みが始まる瞬間（`nextDay`）と新しいキャリアの 1 日目**に、状態の控え（`prepSnapshot`）を状態の中に作る。控えがない日（このバージョンより前のセーブを途中から続けた日）は事故を抽選しない |
| 探索中に控えを上書きしない | — | 控えを作るのは `nextDay` と新規作成のときだけ |
| 前日までの確定データを戻さない | — | 控えは「その日の仕込みの開始時点」なので、前日までの現金・負債・設備・拡張・従業員・評判・実績は控えと同じ。その日に行った購入などは、払ったお金ごと戻る（差し引きはゼロ） |
| 二重計上の防止・二重実行で変わらない | 取引キーがある | 経済の値は足し引きせず、控えの値で丸ごと置き換える（何度実行しても同じ結果）。事故が起きているときだけ受け付け、終わったら事故の記録を消す |
| ローカル・クラウドとの整合 | — | 控えは状態の中にあるので、ローカル・クラウド・ルームの保存にそのまま含まれる |
| 共同経営: サーバーで確定・全員に同期・一度だけ復元 | 権威サーバー | 抽選・発生・復元はすべてサーバーの `applyAction` / `step` の中。リセットはホストだけが実行でき、通知を全員に出す。サーバーは操作を順番に処理するので、同時のリセット要求も 1 回だけ適用される |
| 配信の負担 | — | 控えは差分パッチ・全体送信から除く（サーバーとひとりプレイの両方が持つ必要があるのは本体の状態だけ） |
