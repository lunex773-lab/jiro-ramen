# 共通市場・企業間ランキング 実装前監査（仕様書 10 章・Phase 1）

調査日: 2026-11-04。対象: ブランチ `SecondAKIRA`（d4c4228）。仕様書: 「共通市場・企業間ランキングシステム 実装仕様書」。
このあとの計画と、オーナーに決めてもらう点は `MARKET_RANKING_PLAN.md`。

## 1. 結論（要点）

1. **今のオンライン市場（d4c4228 まで）は、仕様書と時間の進め方が根本的に違う**。
   今は「サーバーの時計で全社が10分ごとに1日ずつ一斉に進む（全店を店主・店長が自動で営業）」。
   仕様書は「各企業が自分の手動プレイで日を進め、JST 午前0時に、いちばん進んだ企業の日付まで、ほかの企業を自動営業で追いつかせる（進行の上限なし）」。
   今の市場の時計（600秒ごと・7日で眠る）は仕様書の進め方に置き換える必要がある（前の判断「市場の1日＝実時間9分」は仕様書の進め方で上書きされる）
2. **市場の中の手動プレイ（一人称の営業）がまだない**（今の市場は経営の操作だけ）。仕様書は手動プレイで確定した日数が進行の基準なので、
   サーバーが「確定した」と言える手動プレイの仕組みが最初に必要
3. **自動営業の計算に、仕様書が求める項目の多くは今のゲームにない**（曜日・季節の需要、疲労、希望シフト、広告、短期バイト、営業時間の短縮、従業員満足度、店舗品質、企業価値）。
   今あるものは同じ規則で動かせる
4. 自動営業を「今の細かいシミュレーションをそのまま回す」形にすると、1店1日あたり CPU 約0.5〜0.8秒。今の「店長の営業（1日単位の計算）」は約0.03ミリ秒（約2万分の1）。
   進行に上限がないので、どちらを選ぶかで Cloudflare の費用と処理の分け方が大きく変わる（6 章）
5. コミュニティ（期間つきの競争）・全体ランキング・期間（週・月・年・累計）・報酬・不正の監視は、まだない

### 6.3 見積もり（6社のコミュニティ1つ、平均2店/社）

いちばん進んだ企業が1日に N 日ぶん手動で進めたとき、ほかの5社（10店）を N 日ぶん自動営業で追いつかせる。

| 1日に進む日数 N | 細かいシミュレーションで追いつく CPU | 1日単位の計算で追いつく CPU |
| --- | --- | --- |
| 10日（約1.7時間のプレイ） | 約65秒 | 約3ミリ秒 |
| 30日（約5時間） | 約195秒 | 約8ミリ秒 |
| 290日（×3速で16時間。上限なしの極端な例） | 約31分 | 約75ミリ秒 |

- 細かいシミュレーションの場合、1回の要求の30秒に収まるように分けて（1回あたり約40店・日）、アラームで続ける必要がある。
  30日/日のコミュニティを100個動かすと、月約5.9億 CPU ミリ秒（Paid で約 $11/月）、DO の稼働 約7.3万 GB-s/月（込みの範囲）。
  Free プランでも DO の30秒は使えるが、稼働時間 13,000 GB-s/日（約2.9時間の計算）で、30日/日のコミュニティは約50個まで
- 1日単位の計算なら、費用はほぼ無視できる（要求の数と保存だけ）
- 手動プレイをサーバーで動かす場合（共同経営と同じ形）、1日あたり実時間約10分の稼働（0.125GB × 600秒 = 75 GB-s/日・人）。
  Free の13,000 GB-s/日では、全体で1日約170人・日まで

**未確認**: 本番の Cloudflare のアカウントが Free か Paid か（リポジトリからは分からない）、workerd での実際の CPU 時間。

## 7. 仕様書と今の実装の矛盾・技術的な問題

| # | 内容 | 影響 |
| --- | --- | --- |
| C1 | 時間の進め方: 今は「サーバーの時計で一斉に進む」、仕様書は「手動で進めた日数＋JST 0時に最大の企業へ追いつく」 | 今の市場の時計を置き換える（今の市場のデータの移行） |
| C2 | 手動プレイの確定: 今のひとりプレイは端末で実時間の dt で動くので、サーバーが結果を確かめられない。仕様書はクライアントの申告を信用しない | 手動プレイをサーバーで動かす（共同経営の仕組み）か、端末を固定刻みにして操作の記録をサーバーで再計算するか（計画の論点 1） |
| C3 | 企業がコミュニティより長く残る（終了後も維持、別のコミュニティへ） | 今は企業が市場の中にだけある。企業を市場の外の Durable Object に出す必要がある |
| C4 | 期間の途中は企業ごとに日付が違う（先に進んだ企業がいる）。客の取り合いを、どの日付の相手と計算するか | 日付ごとの「店の見込み」を記録して、同じ日付の相手と比べる（計画の既定案） |
| C5 | 自動営業で「同じ経済ルール」を使うと重い（細かいシミュレーション）。軽い計算は近似（±15%） | 論点 2 |
| C6 | 自動営業の日に店主がいるか: 今の細かいシミュレーションは店主（プレイヤー）が働く前提。店主がいないと従業員のいない店は1杯も出せず、必ず赤字（仕様書 4.4 の禁止に当たる） | 自動営業では店主をボット（能力は手動より低め）として働かせる案 |
| C7 | ランキングの種類のうち、従業員満足度・店舗品質・企業価値成長率はデータがない。総合評価の配点は根拠が必要 | 論点（後で決める） |
| C8 | 自動経営の方針のうち、営業時間の短縮・広告予算・短期バイト・株式発行・買収は、今のゲームに機能がない | 機能を足すか、方針から外すか（論点） |
| C9 | 0時に手動プレイの途中の企業がいる | その日の営業が終わってから、その企業の同期をする（0時の時点の目標は固定）案 |
| C10 | 日報は60日で捨てている | ランキング（年間・累計）は日報ではなく、確定した日ごとの集計を別に積み上げる |
| C11 | 全体ランキングは、コミュニティごとに進んだ日数と競合が違う | 比べ方（合計か1日あたりか）の論点 |
