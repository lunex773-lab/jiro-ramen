### Phase 2: シフト・勤怠の不具合・社員の単日出勤・店長代理（`8a66c80`）

- **原因**（B1）: 仕込みの時間に、出勤している人の今日の予定を一度「休み」にしてから入れ直すと、勤怠の作り直し（`reapplyToday`）が「退勤（left）の人に予定が戻った」場合を扱っておらず、退勤のまま一日中来なかった。B2・B3: 「シフトを自動で組む」・営業時間の変更が今日の曜日のくりかえしまで書き換え、今日の勤怠は前の予定のまま（画面と実際が食い違う）だった
- **直し方**: 予定と今の状態（来ていない・勤務中・休憩中・帰る途中・退勤済み）を分け、新しい予定で「今いるべき・あとで来る・もう終わった」を1つの規則で決める。すでに起きた実績（出勤の時刻・働いた時間）は消さない。自動で組む・営業時間の変更は「あすから」にして、今日の予定が変わる人は今日の分を前の予定のまま残す
- **データの流れ**: 勤務カレンダー → 操作（`setDateShift` など。画面が見ていた版 `baseRev` つき）→ core が予定（`shifts`・`dateShifts`）を変え、変更の記録（いつ・誰が・前→後）を残す → 今日の予定が変わった人だけ勤怠（`att`）を作り直す → `updateAttendance` が時刻で動かす。共同経営ではホストの操作をサーバーが確かめ、状態の差分をゲストへ配る
- **状態の移り変わり（勤怠）**: 来ていない → 勤務中 ⇄ 休憩中 → 帰る途中 → 退勤済み。予定を変えても、勤務中・休憩中の人は退勤にしない（新しい予定の終わりまで働く）。退勤済みの人に予定を足すと、また来る
- 足したもの: 社員の単日出勤（その日だけ出勤・休み・時間・担当）、その日だけの「店長代理」（店長が休み・欠勤の日だけ店長の仕事をする。日が過ぎると消える）、役目と仕事の表（`data/staff-roles.ts`）
- 変更・追加したファイル: `sim/staff.ts`・`sim/deputy.ts`（追加）・`data/staff-roles.ts`（追加）・`sim/shift-plan.ts`・`sim/stores.ts`・`sim/employees.ts`・`sim/store-manager.ts`・`types.ts`、画面 `ui/manage.ts`、サーバー `protocol.ts`

### Phase 3: 共通市場の途中のセーブ・営業の終わりでの送信・送信待ち（`c8ffc90`）

- **前の問題**: 1日の結果は「翌日の仕込みへ」を押したあとに送っていた。営業の途中は保存されず、通信が切れると「受け取られなかった」と同じに扱っていた
- **データの流れ**: 閉店して精算 → その日を確定（会社の日報・ほかの店の営業。`finalizeDay`）→ 送る本文を端末に残す → サーバーへ送る（チケットの ID で同じ日の重複を数えない）→ サーバーが前の日の状態から確かめる（`verify.ts`）→ 受け取ったら端末の残りを消す。閉店後の事務作業のお金は、送った日の日報を書き換えず次の日の日報に入れる
- **送信の状態**: 集計中 → 送信中 → 確定済み、または 送信待ち（通信が戻ったとき・30秒ごと・次に市場を始めるときに同じ本文を送り直す）。送れるまで次の日へは進めない
- **途中のセーブ**: 2分ごと（変わっていれば）・開店・次の日へ・画面を閉じるとき・市場へ戻るとき・手動。サーバーは版・日・版の番号（古い版は断る）・チェックサムを確かめ、2つの場所へ交互に書いてから目印を変える（途中で止まっても前のセーブが残る）。保存が確かめられるまで「保存しました」と出さない

## 5. 未解決・制限

- **今までのイベントは新しい基盤へ移していない**: バズ・覆面調査員・珍しい客・クレーム・爆発・YouTuber・テレビは、動きと乱数の並びを変えないため処理はそのまま。記録の形（同時のイベント・連鎖のもと）と、同時に起きているイベントのつながりだけを共通にした
- **前のセーブの客の新しい性格**（好奇心・撮影・SNS など）は、平均の値ではなく客の ID から決まる値（客ごとに違う反応にするため）
- **プレイヤーのいない店**（店長の1日の計算）では、珍客・SNS・動画は起きない（簡単な計算のため）。知名度・話題性はその店の状態に残るが、その日は変わらない
- **YouTuber の名簿は店ごと**（計画書では「市場では会社ごと」と書いていた）。店の状態ごと入れ替わる作りに合わせた
- **映り込みへの配慮**は簡単にした: 生配信の企画で、となりの席の、迷惑を我慢しにくい客が少し嫌がる（「店内のみ」の許可なら嫌がらない）
- **iPhone の実機**では確かめていない（Playwright の iPhone の画面の大きさ・タッチで確かめた）
- コミット `76b6527` は、時間の上限で落ちるテストが1つ残ったまま送ってしまった（負荷が高いときに5秒を超えた。中身の誤りではない）。次のコミット `1144022` で時間の上限を延ばした
