# 統合改修設計書（じろ7）の計画

オーナーから受け取った「統合改修設計書・改訂版（混沌系イベント / 星空・昼夜環境 / 従業員シフト改善 / クラウドセーブ / オンライン市場データ同期）」に沿ってゲームを進化させる。
設計書の手順どおり、**Phase 1 で今のコードを調べて計画と質問を出し、承認を得てから Phase 2〜8 を順に作る**。
追加のイベントとして、オーナーの指示「くまのプーさんの来店」も入れる（扱いは 4章の質問 Q1）。

## 1. 今のコードの調査（2026-11-12）

### 1-1. 全体の構造

| 部分 | 場所 | 役目 |
| --- | --- | --- |
| ゲームの計算 | `packages/core`（TypeScript） | 1日の流れ・客・従業員・在庫・お金・イベント・市場・検証。端末とサーバーで同じ計算を使う |
| 端末 | `apps/client`（Vite + Three.js） | 3D の店（`render/world.ts`・`render/models/*`）・画面（`ui/*`）・進行（`game/app.ts`）・通信（`net/*`） |
| サーバー | `apps/server`（Cloudflare Workers） | 共同経営のルーム（Durable Object・`room.ts`）・共通市場（Durable Object・`market.ts`）・セーブとランキング（D1） |
| 配る | GitHub Actions | 端末は GitHub Pages、サーバーは Cloudflare |

### 1-2. ゲーム内の時間

- 1日は **仕込み（prep）→ 営業（open）→ 閉店作業（closing）→ 精算 → 閉店後（closed）→ 翌日の仕込み**。
- 時計の時刻があるのは営業中だけ（`clockMinuteAt(todayHours, openT)`。営業時間は店ごとに決められ、枠が2つ・日またぎもある）。
- 仕込みと閉店作業の間も `s.t`（その日の経過秒）は進むが、時刻としては表示していない。閉店後（事務作業）は時間が止まる。
- 現実の時間（JST）は共通市場の0時の締めにだけ使う（`jst.ts`）。ゲーム内の時間とは別。

### 1-3. 3D の空と明るさ

- `render/world.ts`: 空は**一色の背景（#bcd3e6）と霧**、明かりは**半球光と太陽の平行光が1つずつで固定**。昼夜・夕焼け・星・月はない。
- 店の周りは地域で6種類（都会・駅前・街・住宅街・郊外・田舎。`models/surroundings.ts`）。建物の窓の一部は明るい材質（発光）を使っている。
- 地域のデータ: 市区町村の人口・面積（人口密度）・昼夜間人口比率・小売業と飲食店の事業所数がある（`data/municipalities.ts`・`data/daytime.ts`）。
- 画質の設定（低・中・高）と、端末の速さに合わせて解像度を上げ下げする仕組みがある（`render/resolution.ts`）。カメラの遠い側は 80m。

### 1-4. 従業員・シフト・勤怠

- アルバイト: 曜日ごとのくりかえし（`e.shifts`）と、日にちごとの予定（`e.dateShifts`。くりかえしより優先）。勤務カレンダーで決める。
- 社員: 毎日、仕込みから閉店まで。休みの曜日だけ決められる（`setRestDays`）。**社員の日にちごとの予定（単日出勤）はない**。
- 「シフトリーダー」は**社員の上位の役職**（日給が上がり、全部の仕事をする。`promoteLeader`）。店長がいない・休みの日は、その日に勤務のあるシフトリーダーが店長代理になる（2026-11-12 に入れた）。**日ごとの任命はない**。
- 勤怠: 毎朝 `rollCall` で、その日の予定と欠勤・遅刻を引き、`e.att`（`Attendance`）に出勤・退勤・休憩の予定の時刻と状態（off / scheduled / late / working / break / left / absent / closed）を持つ。営業中は `updateAttendance` がこの予定の時刻で出勤・休憩・退勤させる。
- 当日の予定を変えたら `reapplyToday` がその人の勤怠を作り直す。

### 1-5. 当日のシフト変更で退勤扱いになる不具合の原因（再現できた）

core のシミュレーションで再現した（2人のアルバイト、仕込み → 営業）。

| # | 起きること | 原因 | 場所 |
| --- | --- | --- | --- |
| B1 | **仕込みの時間に、出勤している人の今日の予定を一度「休み」にし、そのあと勤務を入れ直すと、その人は「退勤」のまま一日中来ない**（開店しても来ない）。社員の休みの曜日を付けて外したときも同じ | `reapplyToday` の仕込みの時間の分岐が「退勤した（left）人に予定が戻った」場合を扱っていない（営業中の分岐だけが扱っている）。いったん出勤した印（`arrived`）が残ったままなので、どの分岐にも入らない | `packages/core/src/sim/staff.ts` `reapplyToday` |
| B2 | 「シフトを自動で組む」・営業時間の変更をすると、**今日の曜日のくりかえしの予定まで書き換わる**のに、今日の勤怠は前の予定のまま。勤務カレンダー・シフト表・人件費の見込みには新しい予定が出て、実際には前の予定で動く（画面と実際が食い違う）。知らせの文は「あすから」 | 曜日ごとのくりかえしだけを書き換えて、今日の分を残していない | `shift-plan.ts` `autoShifts`・`remapShiftsForHours` |
| B3 | B2 のあとでその人の今日の予定を変えると、新しい営業時間の分（くりかえし）を今日の営業時間の分として読み、出勤・退勤の時刻がずれる（退勤の時刻を過ぎたことになって帰ることがある） | B2 と同じ（今日の予定と今日の営業時間が合っていない） | `staff.ts` `reapplyToday`・`planTimes` |

ほかに確かめたこと（問題なし）: 出勤済みの人がいるときに別の人のシフトを入れる・消す・毎週にする、営業中に出勤済みの人の退勤を延ばす・早める、休みの人を呼び出す、営業中に「退勤」を勤務に戻す（戻ってくる）。

**データの流れ**: 画面（勤務カレンダー）→ 操作 `setDateShift` / `setShift` / `setRestDays` / `autoShifts` → core が予定（`shifts`・`dateShifts`）を変える → 今日の予定が変わった人だけ `reapplyToday` で勤怠（`att`）を作り直す → `updateAttendance` が勤怠の時刻で動かす。共同経営ではホストの状態がそのままゲストへ送られる。

### 1-6. セーブ

- ひとりの経営: 端末のスロット（3つ）に保存。クラウドへは手動で「上げる・読む」（世代番号と競合の確認あり。`net/cloud.ts`・`api/saves.ts`）。
- 共同経営: ルームの状態をサーバー（Durable Object の SQLite）に定期的にチェックポイントで保存し、操作の ID で二重の適用を防いでいる（`apps/server/src/checkpoint.ts`）。
- **共通市場**: 会社の状態はサーバーにだけある。**営業の途中は保存しない**。途中でやめると、次に始めたときはサーバーの前の日の状態から、その日を初めからやり直す。

### 1-7. 共通市場の1日の送信

- 日の始めに「その日の条件」（チケット）をもらい（`startDay`）、**「翌日の仕込みへ」を押して次の日へ進んだあと**に、その日の状態をまるごと送る（`commitDay`。`game/app.ts` `commitMarketDay`）。
- サーバーは前の日の状態から説明できる変化かを確かめ（`verify.ts`）、受け取ったら会社の状態・日の記録・順位に入れる。**同じチケットの再送は二重に数えない**（最後に受け取ったチケットを覚えている）。
- 送れないときは「もう一度送る／市場の画面へ（この日は送られていない）」を選ぶ。送れるまで次の日は始められない。端末に送信待ちを残す仕組みはない（画面を閉じると、その日は送られていないことになる）。

### 1-8. イベント

- 今あるもの: SNS のバズ・覆面調査員・珍しい客（2種）・理不尽なクレーム・爆発事故・YouTuber・テレビ取材・客を襲う事件。食べ方の汚い客・隣の客の迷惑・店の外の喫煙・団体客（`manners.ts`）。
- 共通の部分（`sim/events.ts`）: 種類ごとの抽選と発生の回数・クールダウン・1日の回数・記録（ID・日時・会社・店・確率・状態・結果）・開発用に起こす。ただし**発生の条件と処理は種類ごとに別の場所に直に書いてあり**（`visitors.ts`・`media.ts`・`accident.ts`）、新しい種類を足すには何か所も変える必要がある。イベント同士のつながり（連鎖）の仕組みはない。
- YouTuber: 撮影の許可をホストに聞き、許可すると撮影し、3日間 SNS のバズの確率が上がる。**一度来たら消える**（登録者数・チャンネル・動画・関係は持っていない）。
- SNS: 店の評判から確率でバズり、しばらく来客が増える。**一般の客の投稿・知名度・話題性はない**（評判は星の数だけ）。
- 店の壁: テレビ取材の出演者のサインを飾っている。店の伝説・珍事件の記録はない。
- 客: 性格の値が12（我慢・値段への敏感さ・味へのこだわり・行儀など）。好奇心・社交性・流行への関心・撮影の傾向はない。
- 音: 音声ファイルを使わず、端末で合成している（`audio/sfx.ts`）。

## 2. 作り方の方針

- 今の仕組みを作り直さず、**足して・直す**。同じ処理を二か所に書かない（例: 昼夜の時刻は core の1つの関数から、イベントの抽選は共通の基盤から）。
- セーブの形は版を上げて、前のセーブを読み込めるように直す（`save.ts` の移行）。
- ゲーム内の時間と現実の時間を混ぜない（空はゲーム内の時刻、市場の締めは JST）。
- 市場の大事な値はサーバーが決める（端末から届いた値はサーバーが確かめる）。ゲストは経営の操作をできない（今のまま）。
- 各 Phase で、core のテスト・サーバーのテスト・E2E を回してからコミットし、SecondAKIRA へ送る。

## 3. Phase ごとの計画

### Phase 2: シフト・勤怠の不具合の修正、社員の単日出勤、日ごとの任命（2026-11-12 済み）

1. **B1〜B3 を直す**（場当たりの条件を足さず、予定と勤怠を分けて扱う）
   - 「今日の予定」は、朝に決めた勤怠（`att.shift`）を正とする。くりかえしの書き換え（自動で組む・営業時間の変更）は**あすから**にし、今日の予定が変わる人は今日の分を日にちごとの予定として残す（画面・人件費の見込みと実際が一致する）。
   - `reapplyToday` を「予定の差分 → 勤怠の作り直し」の1つの関数にまとめ、仕込み中・営業中のどちらでも、退勤済み・未出勤・出勤中・休憩中の全部の場合を同じ表で扱う。すでに起きた勤怠の実績（出勤した時刻・働いた時間・遅刻・欠勤）は消さない。
   - シフトの変更の記録（いつ・誰が・前と後）を従業員ごとに残す。
2. **社員の単日出勤**: 社員にも日にちごとの予定（その日だけ出勤・その日だけ休み・時間）を入れられるようにする。くりかえし（毎日・休みの曜日）とは別に持つ（アルバイトの日にちごとの予定と同じ形を使い、別の店への応援もここで扱う）。
3. **日ごとの任命**: 店長が休み・欠勤の日に、社員を1人、その日だけ任命できる（呼び方は質問 Q4）。任命は日付と店で持ち、その日が過ぎると自動で消える。任命された人は、店長がいないときの仕事（急ぎの仕込み・当日便・翌日の仕入れ・クレームの初期対応・閉店の確認）をする。役目と仕事の対応は表（データ）で持ち、店長だけの仕事（売買・設備・借入・出店・企業間の貸し借り・方針）は任命された人もしない。
   - 店長の欠勤: 朝の出勤確認で店長の欠勤が決まったら、任命された人 → その日に勤務のあるシフトリーダー → 今までの処理（店長がいない店）の順に代わりを決め、勤怠の記録に残す。
4. 画面: 勤務カレンダーで社員の日を選んで単日出勤・任命・取り消しができる。日にちごとの予定・任命は見た目で区別する。変更の記録を見られる。
5. テスト: 設計書 2-5・3-5 の全部（出勤済みの人がいるときの追加・時間の変更・退勤済みの人の編集・営業中の追加と削除・日付が変わる直前・セーブと読み込みのあと・共同経営でホストが変えたときのゲストの表示）。

### Phase 3: 共通市場の途中のセーブと、営業の終わりでの送信（2026-11-12 済み）

1. **営業の終わりで送る**: 閉店して精算した時点（閉店後の事務作業の前）でその日の状態を送り、サーバーが確かめて受け取ったら「確定済み」にする。事務作業（発注・採用など）と次の日への移りは、次の日の送信に含める（サーバーの確かめ方 `verify.ts` を「閉店後の状態」に合わせて直す）。0時の締め・遅れた会社の自動営業・会社どうしの進み方は変えない。
2. **二重に数えない**: 今のチケット（その日の ID）に加えて、送る結果に `市場・会社・営業日・版` の ID を付け、サーバーは同じ ID の再送を一度しか数えない。
3. **送れないとき**: 端末に送信待ちとして保存し（画面を閉じても残る）、「送信待ち」を出して、通信が戻ったら送り直す。確定の返事が来たら送信待ちを消す。
4. **途中のセーブ**: 営業の途中・事務作業の途中の状態を、サーバーの会社ごとに1つ保存する（版の番号・チェックサム・断片に分けた保存・古い版で上書きしない・保存が確かめられるまで「保存しました」と出さない）。保存するのは手動・大事な操作のあと・一定の間隔（2分ごとを予定）・画面を閉じるとき・営業の終わり。
   - 再開: 続きのセーブがあればそこから（ゲーム内の時刻・客・従業員・在庫・売上を戻す）。なければ今までどおり前の日の状態から。
   - 途中のセーブは「続きを始める場所」にだけ使い、確定する値はこれまでどおり、日の終わりにサーバーが前の日の状態から確かめる（途中のセーブで市場の時間を戻したり、他社の進行を消したりしない）。
   - 複数の端末: 新しい版だけを受け付け、古い端末からの保存は断る（「ほかの端末で進んでいます」と出す）。
5. 画面: 保存中・保存しました・送信待ち・通信できません・送り直し中、送信の段階（集計中・送信中・確認中・確定済み・送信待ち）を出す。

### Phase 4: 昼夜・星空・街の明かり（2026-11-12 済み）

1. core に「今のゲーム内の時刻（0〜24時）」を出す関数を1つ作る（仕込みは開店前の朝〜開店、営業中は時計の時刻、閉店作業は閉店の時刻から進む、閉店後は質問 Q5）。月の満ち欠けはゲーム内の日付（29.5日で一巡り）から。
2. 空: 大きな球の内側にグラデーション（時刻で深夜・夜明け前・朝焼け・朝・昼・夕方・夕焼け・日没・夜を滑らかにつなぐ）。太陽と月の位置、月の満ち欠け、薄い雲。
3. 星: 1回だけ作る点の集まり（数は画質で 1,500〜6,000 個）。明るさの違う星を自然な分布で並べ、明るい星は少なく、瞬きはシェーダーで星ごとに違う速さ・位相（CPU を使わない）。昼は描かない。
4. 光害: 地域の人口密度・建物の密度（周りの種類）から 0〜1 の値を1つの式で出し、空の明るさ・見える星の数・地平線の明るさ・地上の明かりを変える（地域ごとの手作業の設定は作らない）。都会でも星は少し見え、田舎でも地上は真っ暗にしない。
5. 街の明かり: 夜は建物の窓・街灯・看板・車のライトを、発光する材質（本物の光源は少しだけ）で点ける。距離が遠いものはまとめて描く。店の中の明かりは時刻で変える。
6. 負荷: 画質の設定と解像度の自動調整に合わせ、iPhone の Safari で確かめる。

### Phase 5: 独立したイベントの基盤

1. イベントの定義を表（データ）で持つ: 種類・発生の条件・確率・発生の時刻・終わりの条件・参加者・対象の店・結果・経営への影響・関連するイベント・再発生の制限・セーブの状態。
2. 共通の部分: 抽選（条件・確率・クールダウン・1日の上限・同時に起きる数の上限・大事さの順）と、種類ごとの処理（始まる・進む・終わる）を分ける。新しい種類は、定義と処理を1つ足すだけで入れられる。
3. つながり（連鎖）: あるイベントの結果が、条件が合うときだけ別のイベントの確率を上げる・起こす（必ずではない。確率・クールダウン・連鎖の深さの上限で無限につながらない）。
4. 今のイベント（バズ・覆面調査員・珍しい客・クレーム・爆発・YouTuber・テレビ）を、動きを変えずにこの基盤へ移す（記録・テストはそのまま通す）。
5. 記録とセーブ: 起きたイベントの記録（今の記録を広げる）・セーブと読み込み・共同経営への同期。

### Phase 7: YouTuber・SNS・店の伝説
