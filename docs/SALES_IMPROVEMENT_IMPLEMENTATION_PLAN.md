# 営業改良: 実装計画（Phase 0）

`SALES_IMPROVEMENT_GAP_ANALYSIS.md` の埋め方を、フェーズごとの作業と完了条件にしたものです。
各フェーズは完了条件を満たしてから次へ進みます。

## 設計の判断（調査結果と理由）

| # | 判断 | 理由 |
| --- | --- | --- |
| 1 | イベントの状態は `GameState.events`（任意の項目）。セーブ形式の版（`SCHEMA_VERSION`）は上げない | 古いセーブはこの項目がないだけなので、読むときに既定値で補えば移行は不要。上げると古いクライアントで読めなくなる |
| 2 | イベントの抽選はイベント専用の乱数 `events.rng` で引く | `s.rng` を使うと、イベントが起きなくても以後の乱数がすべてずれ、既存の挙動とテストが変わる |
| 3 | 数値はすべて `BALANCE.events`、セリフ・投稿文・クレーム文は `data/events.ts` | 設計書 9（数値を散在させない）、D-3（セリフはデータで管理） |
| 4 | SNS バズは来客の倍率だけを変える | 設計書 8（実際の来客・注文フローを通す）。売上は通常どおり提供時に計上されるので二重計上が起きない |
| 5 | 提供前のクレームの「返金」は食券の払い戻し（注文の取り消し・お金は動かない） | 売上は提供時に計上する仕様のため。提供後の返金は従来どおり |
| 6 | 覆面調査員の評価は退店時の満足度の項目そのもの。公開は翌日の仕込みの開始時 | 設計書 C（実際の営業状態から・運任せにしない・一定時間後に公開） |
| 7 | 爆発事故の抽選は「開店の操作の中で 1 日 1 回」。当たったら営業中の時刻を決めて予約 | 「営業日単位」を明確にし、セーブ・ロードで再抽選しないため |
| 8 | 仕込み開始時点の控え `prepSnapshot` は、`nextDay` で仕込みが始まる瞬間と新規キャリアの 1 日目に作る。状態の中に持つ | 状態と控えが同じ保存先・同じトランザクションに入るので、ずれない。控えがない日は事故を抽選しない |
| 9 | 控えには、営業中に変わらない「日報・口コミ」と、接続で変わる「プレイヤー」を入れない | 大きさを抑える。プレイヤーは今の顔ぶれのまま位置と手元を仕込みの開始時と同じにする（共同経営で途中参加した人を消さない） |
| 10 | 復元は控えの値で丸ごと置き換える。ID の連番・乱数・発生頻度の記録・状態の版番号は今の値を使い続ける | 置き換えなので二重に実行しても同じ結果。ID を使い回さない（描画の取り違え・パッチの不整合を防ぐ）。同じ日に事故が再び起きない |
| 11 | 共同経営では控えを差分パッチ・全体送信から除く | クライアントは控えを使わない。毎日の配信量と比較の計算を増やさない |
| 12 | 事故の演出（閃光・揺れ・暗転・文字・目覚め）は client。core は段階と経過時間だけ | ロジックと演出の分離。演出が失敗しても状態は壊れない |
| 13 | 共同経営のリセットはホストだけ（次の日へ進むのと同じ扱い） | 店全体を巻き戻す操作のため。全員に通知する |
| 14 | 事故は 2 日目以降。チュートリアル中はすべてのイベントを止める | 初日やチュートリアルを壊さない |
| 15 | テスト用の強制発生は core の関数と、ひとりプレイ専用の操作 `debugEvent`。画面からは URL に `?debug=1` を付けたときだけ経営メニューに出す | 共同経営で 1 人のクライアントがサーバーの状態を変えられないようにする（サーバーは受け付けない） |

## 未確定（オーナーに確認すること）

推測で確定せず、上の判断で仮に実装し、完了報告で確認します。

1. 爆発後の「死亡の表示」: 倒れて動かない人物（焦げた色・血や傷の描写なし）と、「誰ひとり動かない」という文で示す。この表現でよいか
2. D-1 のセリフは設計書の文言（伏字を含む）のまま表示する。App Store 公開時の年齢区分に影響しうる
3. 0.001% は通常のプレイでは事実上起きない。確認用の強制発生（`?debug=1`）以外に、プレイヤー向けの手段が要るか
4. 共同経営でリセットできるのはホストだけ、でよいか
5. 事故のあとは、リセットしないと営業を続けられない（探索は任意。タイトルに戻っても状態は残る）。別の結末（閉店・やり直しを断る）が要るか

## Phase 1: 共通イベント基盤

- 型: `ShopEvents`（`stats` / `rng` / `buzz` / `critic` / `effects` / `accident` など）、`Customer` に `complaint` / `special` / `look` / `partyId` / `fromBuzz` / `sayStyle` を任意の項目で追加（`types.ts`）
- `sim/events.ts`: 既定値の補完 `ensureEvents`、記録 `noteDraw` / `noteFire`、クールダウン、来客の倍率 `eventDemandFactor`、強制発生 `forceEvent`
- `BALANCE.events` と `data/events.ts`
- 操作 `debugEvent`（ひとりプレイ専用。サーバーの `SOLO_ONLY_ACTION_TYPES` に追加）
- 完了条件: イベントが起きない設定で既存のテストがすべて通る。決定性のテストが通る

## Phase 2: 営業イベント

- SNS バズ: 抽選・倍率・通知・SNS を見て来た客
- クレーム: 原因の追加（遅延・汚れ・理不尽）、対応 5 種、提供前後の区別、重複防止、従業員の対応
- 覆面調査員: 抽選・評価・翌日の公開・評判と来客の倍率・改善点
- client: 操作ボタンの絵文字、上部のバズ表示、詳細欄のクレーム内容、調査員の結果画面、効果音
- 完了条件: 必須テスト（SNS バズ・クレーム・覆面調査員）を単体テストで確認

## Phase 3: 珍しい客

- カップル（金髪の女性と彼氏）: 2 人で並ぶ、隣の席を優先、近くにいるときに一度だけ話す
- 一人客: 食事中に一度だけ小声で話す（満足しているときだけ）
- client: 見た目の上書き（金髪・女性）、小声の吹き出し
- 完了条件: 2 種類のセリフが一度だけ出る、通常の行動（注文・食事・会計）が変わらないことを単体テストで確認

## Phase 4: 爆発事故

- core: 控えの作成、開店時の抽選、予兆 → 壊滅、営業処理の停止、操作の制限、復元 `accidentReset`
- client: 予兆（湯気・火花・警報音）、閃光・揺れ・爆発音・暗転、「数時間後」の文、目覚め、焼けた店内（材質・倒れた椅子・散らばった丼・倒れた人物・煙・残り火・照明の点滅・環境音）、「リセットする」ボタン
- 完了条件: 強制発生 → 営業停止 → 探索 → リセット → 仕込み開始時点と一致 → 再び営業できる、を単体テストと E2E で確認。セーブ・ロードを挟んでも復元先が壊れない

## Phase 5: 共同経営

- サーバー: `accidentReset` を受け付ける（ホストのみ）、`debugEvent` は受け付けない、控えを配信から除く、仕込みの開始・リセット時にチェックポイント
- 完了条件: workerd 上のテストで、全員が同じ事故状態を受け取る、同時のリセット要求で復元が 1 回だけ、ゲストはリセット・強制発生できない

## Phase 6: 総合テスト

- 型チェック、core・server・client の単体テスト、E2E、本番ビルド
- 長期シミュレーション（balance.test.ts）で、イベントがあっても経済が破綻しないこと
- 完了報告（設計書 12）
